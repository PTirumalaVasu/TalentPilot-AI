# 04.1: Skills Tab (Content Sourcing)

**Scenario:** 04: Rita's Content Curation
**Page Number:** 04.1
**Created:** 2026-09-08
**Method:** Whiteport Design Studio (WDS) — Phase 4 UX Design

## Overview

**Page Purpose:** Let Rita see every Skill in the system, and for any Skill, source a learning-content link herself (search YouTube/Udemy or paste a link directly), review it, and approve it as Content — closing a content gap immediately instead of waiting on the nightly batch-matching job.

**Entry Point:** Primary Navigation — Rita clicks "Skills" in the header nav (existing nav item; this page is what it opens to). Also reachable from the Skill Assignment Flow's (03.1) "No approved content found yet for this skill" state via a "Source content" link.

**User Mental State:** Rita has just hit a content gap (a Skill with no or thin approved Content) and wants to fix it herself, right now, without needing engineering help or waiting for tomorrow's ingestion run.

**Main User Goal:** Find and approve a good piece of Content for a specific Skill in under a minute.

**Business Goal:** Fast, relevant content discovery (Trigger Map Objective 5) — extended to cover the admin-curation gap-filling path alongside the primary AI-matched batch path (§4.2).

**URL/Route:** `/skills`

#### Main Content: Skills Card Grid

`[UPDATED 2026-09-08]` Changed from a data table to a card grid — the earlier table-with-count-badge design made Rita open a modal just to see *what* was already approved for a Skill. A card surfaces the actual approved link inline, so "does this Skill already have something good?" is answerable at a glance, without opening Content Lookup at all.

`[UPDATED 2026-09-08]` Each card shows **exactly one** approved link, never a list — mirrors the Employee-facing "always show exactly one curated recommendation per Skill, never a list of candidates" rule already locked for Content Discovery (PRD §4.2/FR-4). If more than one item has ever been approved for a Skill (FR-18 permits approving more than one at a time), the card surfaces only the current one (the most recently approved) — consistent, not a regression from FR-18's "one or more" language, which governs what can be *attached*, not how many show on this summary card.

`[REMOVED 2026-09-08]` `skills-tab-btn-find-content` no longer exists on this page. It was first scoped to every card, then narrowed to assigned-only cards (to preserve a content-sourcing entry point for locked Skills), then **removed entirely, from every card, per direct feedback** — see the Known Gap note below.

**Skill Card contents:**
1. **Header row** — Skill name + a badge: green "✓ Approved" when a link is approved, amber "⚠ None yet" when not (mild warning tone, not error — this is the exact gap this page exists to close)
2. **Utility row (FR-21/FR-22)** — directly under the header: **unassigned** Skills show small Edit (pencil) and Delete (trash) icon buttons; **assigned** Skills show a 🔒 lock icon with a tooltip/inline label "Locked — assigned to an Employee" in their place — never silently omitted, so Rita always knows *why* she can't edit a given Skill, not just that she can't.
3. **Body** — when approved: **one** row showing the current approved Content item's source (YouTube/Udemy), its title as a button that opens the Watch Modal, and a compact days-to-complete (e.g., "≈2d"). When not approved: "No approved content yet for this skill."
4. `[UPDATED 2026-09-08]` **No footer action, on any card.** Unassigned Skills reach content-sourcing via Edit (utility row). Assigned Skills have **no content-sourcing entry point on this page at all** — flagged as a known gap below (PRD Open Question 17), not silently resolved by omission.

**Known gap — assigned Skills and content-sourcing (PRD Open Question 17):**

FR-17/18/19/23's own wording states content-sourcing/rejection is not gated by a Skill's assignment status — only Skill *identity* (rename/delete, FR-21/22) is locked. In practice, though, this page currently gives an assigned Skill no way to reach that capability: a "Find Content" button was tried as the locked card's entry point, then removed from every card the same day per direct feedback, without a replacement named. Two ways to close this, not decided in this spec:
- Narrow FR-17/18/19/23 to unassigned Skills only, matching what the UI actually allows today (simpler, but changes those FRs' stated scope); or
- Design a different entry point for assigned Skills — e.g., reachable from the Provenance Drill-Down modal (01.2), alongside other per-Assignment detail, rather than from this page's card grid.

Not a blocker for the unassigned-Skill path (Edit/Delete/content-sourcing all work as specified there) — only affects a Skill once it's been assigned.

#### Watch Modal (opened from any content link — a candidate's [View], or an already-approved link on a Skill card)

`[ADDED 2026-09-08]` Every content link in this page opens in-app, never a bare new-tab redirect — a candidate under review (FR-18 pre-approval) and an already-approved link on a Skill card (§4.6 UX spec, "single link shown") both use this same popup.

| Object ID | Component | Type | Content (English) |
|-----------|-----------|------|----------|
| `watch-modal-title` | Title | Text | Content title |
| `watch-modal-meta` | Metadata | Text | Source · duration · days-to-complete |
| `watch-modal-btn-close` | Close Button | Icon Button | [X] |
| `watch-modal-body` | Preview Area | Embed or fallback (16:9) | Embedded player (YouTube) or a "preview not available" state (Udemy, most manual links) |
| `watch-modal-open-external` | Open-External Link | Link | "Open in new tab ↗" — always present, primary path when no embed exists |

**Preview behavior:**
- **YouTube** links embed the actual video inline (an `<iframe>` against the source's own player) — Rita watches without leaving the product.
- **Udemy and most manually-pasted links** cannot be embedded (no reliable third-party embed support) — the preview area shows a clear "Preview not available for {source} in this prototype" state instead of a broken/blank frame, with "Open in new tab" as the explicit way to actually watch it.
- Closing the modal (via [X], the "Close" footer button, or approving/leaving the underlying flow) stops any playback — the embed is torn down, not just visually hidden.

### Form Validation & Requirements

**New Skill (create) / Content Lookup Edit Fields (edit):**
- Name: required, non-empty; checked case-insensitively against other existing Skill names before create/save (FR-20/FR-21's duplicate handling) — edit's check excludes the Skill's own current name (renaming "Python Basics" and resubmitting "Python Basics" isn't a duplicate).
- Description: optional, no format constraint.
- Edit and Delete are only ever reachable for a Skill with zero Assignments (FR-21/FR-22) — the controls don't render at all on a locked Skill's card, so there's no client-side "disabled but visible" state to validate around; the server-side gate (whichever module ends up owning `skills`, per PRD Open Question 16) is the actual enforcement point.

**Content Lookup — Search:**
- At least one source must be enabled (have a configured credential) to search; if neither is configured, only "Paste a link" is available.

**Content Lookup — Paste a link:**
- URL: required, must be a well-formed URL (client-side format check only — no reachability/content check, per FR-17a: "HR Admin is responsible for the link being correct").
- Title: required (candidates need a title to display/approve).
- Duration: optional; free text, parsed to hours for the FR-19 estimate if supplied in a recognizable format (e.g., "2h 30m"), otherwise the days-estimate is simply omitted.

**API Keys:**
- YouTube key: required non-empty string to save; no further format validation beyond "not empty" (real validation happens at first search, per PRD FR-16's "invalid or revoked key produces a clear error at the point of lookup").
- Udemy credential: client ID + client secret, both required non-empty to save.

### Accessibility Requirements

- Content-count badges use **text + icon**, never color-only for the "None yet" warning state (WCAG AA, consistent with PRD NFR-A2).
- Content Lookup and API Keys modals are fully keyboard-operable: Tab order follows visual order, Escape closes, focus returns to the triggering button on close.
- Source toggle (YouTube/Udemy) and tab group (Search/Paste a link) are operable via arrow keys, consistent with standard tab-widget behavior.
- Approve success toast is announced to screen readers (matches PRD NFR-A4's existing toast-announcement pattern).
- All buttons have descriptive labels (not icon-only), except the modal close [X], which carries an `aria-label="Close"`.
- `[ADDED 2026-09-08]` The lock indicator (🔒) on an assigned Skill's card carries an `aria-label`/visible text equivalent ("Locked — assigned to an Employee"), not icon-only — same WCAG AA bar as the badges above (PRD NFR-A2). Edit/Delete icon buttons on unassigned Skills carry `aria-label="Edit"`/`aria-label="Delete"`.

### Real-Time Updates Architecture

**For POC:** No polling needed — this page is admin-triggered and synchronous (search, approve). The Skills Card Grid's per-card count badge and link list refresh when the Content Lookup modal closes, not via background polling.

## Content Rules

**Search vs. Recommended — Non-Negotiable:**
- ✅ Content Lookup results are always labeled "Search Results," never "Recommended" — that word is reserved for the AI-matched Content shown to Employees (§4.2). Conflating the two would undermine the "✓ Approved" trust signal already established there.
- ✅ A manually-pasted link gets the identical review/Approve treatment as a searched result — never auto-attached just because it was typed in.
- ✅ Days-to-complete is shown only when a real duration is known — never estimated or guessed from a missing value (same "no match beats a bad match" principle as FR-3).

**Copy Tone:**
- Factual and efficient (HR-facing), matching 01.1/03.1's established tone — no encouragement copy, no color-only signaling.
