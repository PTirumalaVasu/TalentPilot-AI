## Overview

**Page Purpose:** Rita sees the system-generated password, shown exactly once, and copies it to share with the new hire out-of-band.

**Entry Point:** Automatic — fires immediately on successful submission of the Create Employee form (05.2). Also reused by 05.1's "Regenerate Password" action (FR-28), scoped to whichever Employee triggered it.

**User Mental State:** The scenario's success moment — Hope realized if this is quick and clear; Worry confirmed if the password gets lost with no easy recovery.

**Main User Goal:** Copy the password and close, confident there's a fallback (Regenerate) if it's lost.

**Business Goal:** Same as 05.1/05.2 — closes the roster-provisioning gap; this specific screen is what makes the login provisioning actually usable in practice.

**URL/Route:** N/A — modal, opened over `/employees`

**Content note:** The mock currently reuses "Employee created" as the title even when opened via Regenerate. `[FLAGGED DURING SPEC SYNC]` A real build should make the title conditional — "Employee created" (from 05.2) vs. "Password regenerated" (from FR-28's Regenerate action) — since "created" is misleading when the Employee already existed. Not fixed in the mock (out of this spec's drafting scope), logged so it isn't silently carried into a real build.

---

### Content (English Only)

- Title (create path): "Employee created"
- Title (regenerate path, per the flagged fix above): "Password regenerated"
- Summary: "Share this password with {Employee name} — it won't be shown again."
- Recovery note: "Lost this before sharing it? Use \"Regenerate Password\" from the employee's row — a lost password is a quick fix, not a dead end."
- Copy button: "Copy" → on click, shows a brief toast: "Password copied to clipboard"
- Close action: "Done"

---

### Interactions & Behaviors

| Object ID | Event | Action | Destination |
|-----------|-------|--------|-------------|
| `password-reveal-btn-copy` | Click | Copy to clipboard | Toast confirms; panel stays open |
| `password-reveal-btn-done` | Click | Close panel | Returns to 05.1; the new/updated Employee is visible in the list — **scenario success ✓** |

---

### Page States

| State | When | Appearance | Actions |
|-------|------|------------|---------|
| **Shown** | Entered from 05.2 (create) or 05.1's Regenerate action | Password value populated, Copy + Done available | Copy, Done |
| **Copied** | Copy clicked | Brief toast confirmation; value remains visible (not hidden after copy — Rita may need to copy again if the toast is missed) | Copy again, Done |
| **Closed** | Done clicked | Panel removed; password is never retrievable through the UI again (server-side one-time-reveal enforcement, not a client-side "already viewed" flag) | (returns to 05.1) |

---

### Form Validation & Requirements

None — this is a read-only display panel, no input fields.

---

### Accessibility Requirements

- Password value is presented as selectable text (not an image or canvas render), so screen readers and copy-paste both work normally.
- "Copy" action's toast confirmation is announced to screen readers (matches PRD NFR-A4's toast-announcement pattern).
- Modal is keyboard-operable: Tab order follows visual order, Escape triggers the same action as "Done."

---

## Content Rules

**Security-critical framing:** This panel must never imply the password can be retrieved later through any UI path other than Regenerate (FR-28) — the recovery note exists specifically so Rita never needs to contact engineering, closing the loop the Trigger Map's chore-relocation fear is testing.

---

## Out of Scope (this page)

- Emailing the password directly to the new hire — no email-sending infrastructure exists in this stack (PRD §9); sharing is always out-of-band, by design.
- Displaying the password again after this panel closes, under any circumstance — Regenerate (FR-28) issues a *new* password; it does not reveal the old one.

---

## Design Constraints

- **Responsive:** Desktop-primary, same as 05.1/05.2.
- **Security:** The password value must never be logged, sent to analytics, or included in any error report if the copy action fails — copy failures should fail silently to a manual-select fallback, not surface the password in a console/log message.
