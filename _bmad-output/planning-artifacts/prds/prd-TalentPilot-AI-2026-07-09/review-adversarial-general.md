# Adversarial Review — TalentPilot-AI PRD (2026-09-11 update: §4.7 Employee Roster Management, §4.8 HR Admin Navigation Shell)

Scope: this review targets only the material added/touched in the 2026-09-11 update — §4.7 (FR-24–27), §4.8 (FR-28), the addendum's new "Employee Roster Management — Architecture Handoff Notes," the Open Question 9 edit, and their interaction with the rest of the already-shipped PRD. Already-built epics (§4.1–4.6) are treated as settled and are only referenced where the new material contradicts them.

- **The PRD's central claim for this update — that the Employee CRUD "replac[es] the previous hand-seeded/demo employee list ... as the system's source of truth" (§4.7 description) and that Open Question 9(b) is "RESOLVED" — is not actually true for the HR Admin side, and the addendum's own file references prove it.** The addendum names two *separate* existing stores: the `employees` table (`app/assignments/models.py::Employee`) and the mock credential store in `auth/repository.py` (a plaintext Python dict, used for login). FR-24 explicitly provisions EMPLOYEE-role accounts only. Nothing in §4.7, FR-24–27, or the architecture handoff notes says how (or whether) the login/auth code path is repointed from `auth/repository.py` to the `employees` table, and nothing addresses what happens to the HR_ADMIN account(s) that currently live in that same hardcoded dict. The result: after this ships, Employee logins are hashed-password/real-table-backed while the (at least one) HR Admin login almost certainly keeps running on the plaintext-dict comparison this update was framed as retiring. The Glossary edit and §4.7 description state the replacement as settled fact; Open Question 9 hedges it as "partially resolved"; neither version is accurate, and the two sections contradict each other on how resolved this actually is.

- **The single most load-bearing integration point of this entire feature — swapping the auth layer's data source from `auth/repository.py` to the `employees` table — is absent from the addendum's "Architecture Handoff Notes," even though that section's stated purpose is to flag exactly this kind of load-bearing implication before the architecture pass starts.** The five bullets there cover schema migration, password hashing, password generation, soft-delete, and the nav shell — but never the login-flow rewire itself, which is arguably the riskiest part of the whole feature (it's the thing that turns "cosmetic CRUD" into "who can log into this system at all").

- **No provisioning path exists for HR_ADMIN accounts at all, and the PRD treats this as a someday-problem rather than a live gap.** FR-24's own note and Open Question 9(a) both defer this with "revisit if a second HR Admin is ever needed" — but a first HR Admin account is needed *today*, on day one of this feature, and nothing in the PRD says how that account was or will be created, rotated, or recovered if its credential is lost. This is a single point of failure for the entire product (no HR Admin login → no one can assign anything, manage the roster, or use the dashboard) and it is dismissed rather than flagged as an open risk requiring a decision before launch.

- **Existing Assignment data tied to the five hardcoded demo employees is a silent casualty of this update.** The task context states 5 epics are already built/in-progress against this PRD — meaning Assignments, watch-progress rows, and possibly HR Overrides almost certainly already exist referencing the current hand-seeded employee records. §4.7 introduces a new employee lifecycle (real table, new columns, password hashing) but never says what happens to those existing demo employees and the live data pointing at them: are they migrated into the new schema (and if so, with what password, since they never went through FR-24's generation flow)? Deleted and their Assignments orphaned? Left running on the old shape indefinitely alongside newly-created real employees? This directly collides with §9's "No data migration. The dashboard launches clean on 2026-07-13" constraint, which was written for the original launch and is now stale but never revisited in this update despite the update creating exactly the kind of migration need that constraint was written to rule out.

- **FR-27's "an archived Employee's login is deactivated immediately" is not obviously compatible with the stateless JWT session mechanism this PRD already locked (§4.5, addendum Technical Stack).** A JWT in an HTTP-only cookie is, by construction, self-validating until expiry unless the server performs a per-request liveness/active-status check against the issuing record. FR-13 implies signing-out invalidates a session "immediately," which suggests *some* server-side revocation capability already exists — but that mechanism is never described, and FR-27 silently assumes it extends to "employee got archived mid-session" without stating this as a requirement on session validation. If the real implementation is pure stateless JWT with no revocation list, an archived Employee's existing (unexpired) cookie will continue authenticating successfully, directly contradicting the FR-27 consequence as written. This should be an explicit NFR ("every protected request re-validates the employee's active/archived status server-side"), not an implied side effect.

- **The auto-generated password flow has no recovery or rotation path, and the gap is worse than the addendum admits.** FR-24 generates a password shown once; FR-26 lets HR edit any field except Employee ID/Code but says nothing about resetting a lost/forgotten password; FR-27 only covers delete/archive. If an HR Admin fails to record the one-time password (closes the tab, screen times out, whatever), or an Employee forgets it, there is no FR anywhere for "HR Admin regenerates/resets an Employee's password." Given the stated constraint that no email-sending infrastructure exists, this isn't a hypothetical edge case — it is the *only* recovery mechanism this system could plausibly offer (out-of-band re-share, same as initial provisioning), and it's simply missing from the FR list.

- **No forced password change on first login, and no password policy of any kind, is specified — a real security/trust gap given this product's own stated positioning.** Because HR Admin generates and reads the password once, HR permanently and knowingly possesses every Employee's login credential unless the Employee independently changes it — and no FR gives the Employee a way to change their own password (Employee Profile View is explicitly deferred, §6.2). Combined with SM-C2's explicit goal that "Employee sentiment around being 'watched' should not rise," an HR function retaining indefinite knowledge of employees' login credentials is arguably a bigger trust violation than watch-progress tracking, yet it goes completely unaddressed — no forced first-login password change, no minimum length/complexity requirement, no expiry policy.

- **Email uniqueness handling is specified with less rigor than the directly analogous Skill-name duplicate check earlier in the same PRD.** FR-20 (Skill creation) explicitly states duplicate detection is case-insensitive. FR-24's Email-uniqueness consequence does not specify case-insensitivity at all, despite Email now doing double duty as both a profile field and the literal login identity — an area where case-handling ambiguity (or inconsistency with whatever the eventual login comparison does) is far higher-stakes than for a Skill name.

- **Email-uniqueness rejection is a textbook user-enumeration side channel, and it's introduced by this update without acknowledgment.** "Attempting to create a second Employee with an already-used email is rejected with a clear message" (FR-24) means anyone with HR Admin access (or anyone who compromises that single, weakly-secured HR Admin account — see above) can probe arbitrary email addresses and learn which ones already exist as Employee accounts. Low severity given the role is already privileged, but it's exactly the kind of thing an adversarial security pass on an auth-adjacent feature should name rather than skip.

- **FR-25's roster filtering by Department is a testable consequence written against a field whose backing schema is explicitly unresolved.** The addendum states "Whether `department` reuses the existing `group` column or is a distinct new column is an open implementation call, not decided in the PRD" — yet FR-25 asserts, as a testable consequence, that the roster "is searchable/filterable by at least Name, Department, and Position/Job Title." A consequence can't be meaningfully verified against a field whose very existence/source hasn't been decided; this should either be flagged as contingent or resolved before FR-25 is treated as spec-complete.

- **FR-28's own stated consequence ("same three entries on every HR Admin page") is undercut by its own Notes.** The FR asserts this as a testable, unconditional consequence, but the accompanying architecture note admits `SkillsPage.tsx` "likely duplicates the same top-header nav (not yet confirmed)" and would need separate treatment for the consequence to hold. An FR whose testable claim depends on an unconfirmed fact about a second file isn't actually testable yet — it's testable *pending confirmation*, which should be stated as such rather than asserted flatly.

- **No architectural guardrail is stated to keep the new Employees page inside the "coaching-only" data-access boundary (§9) or the "not a manager-facing tool" Non-Goal (§5).** §4.7 captures a "Manager Name" free-text field on every Employee record with no stated purpose, no consumer FR, and no access-control statement. Given this PRD already treats "coaching-only" as a structural, data-access-layer enforcement requirement (§8, §9) for Watch Progress specifically, the silent addition of manager/org-chart-shaped data with no equivalent access statement is worth flagging — it's not shown to violate anything, but it's also not shown to have been checked, and the product's only prior mention of "manager" is to explicitly rule the role itself out (§2.2, §5).

- **§4.7's employee identity model introduces a second unique key (Employee ID/Code) whose relationship to deletion/reuse is unspecified.** FR-24 requires Employee ID/Code uniqueness and immutability (FR-26); FR-27 allows hard-delete when no Assignment history exists. Nothing states whether a hard-deleted Employee's ID/Code becomes available for reuse by a later, unrelated hire — a real-world HR data-integrity question (reusing an ID/Code that appeared in old exports, tickets, or conversations against a different person) that the PRD doesn't even flag as open, unlike the comparable Skill-identity questions in §4.6 which got explicit `[ASSUMPTION]` tags.

- **The "shown once, never re-displayable" password guarantee is asserted as a Consequence (FR-24) before the mechanism that would enforce it exists.** The addendum admits the enforcement approach (client-side discipline vs. a server-side one-time-reveal flag) is unspecified and open for the architecture pass. A "never re-displayable" claim enforced only client-side is not actually a security guarantee — a client with dev tools open, or a slightly-earlier network response, can defeat "client-side discipline" trivially. The PRD states this as a testable consequence without acknowledging that only one of its two candidate mechanisms would actually make it true.
