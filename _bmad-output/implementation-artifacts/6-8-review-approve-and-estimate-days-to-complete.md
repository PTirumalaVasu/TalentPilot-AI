# Story 6.8: Review, Approve & Estimate Days-to-Complete (FR-18, FR-19)

Status: done

## Story

As an **HR Admin**,
I want to approve one candidate as Content for a Skill, seeing an estimated days-to-complete first,
So that Employees assigned that Skill see a real, HR-approved recommendation immediately — not through the batch job's schedule.

## Scope Notes (read before starting)

1. **This story is API + a frontend slice pulled forward from Story 6.10, by explicit user instruction** ("start development api and ui for the story 6-8 ... the ux design if required") — same kind of deviation Story 6.7 already made from Story 6.6's API-only precedent. Story 6.10 owns the *whole* Skills tab (Card Grid, Content Lookup Panel shell, Edit/Delete, the Search tab's own Approve wiring, Reject wiring). **This story's frontend scope is narrower: only wire up the `[Approve]` button that Story 6.7 already built — visibly present but hard-`disabled` — on `ManualContentEntryForm.tsx`'s candidate card** (`frontend/src/features/admin/ManualContentEntryForm.tsx:126-133`, `title="Available once Story 6.8 ships"`). Do not build the Skills Card Grid, the Content Lookup Panel shell, Search-tab result cards, or Reject — those stay Story 6.10/6.9's job, still `backlog`.
2. **The days-to-complete estimate is already built and already displayed — nothing to add there.** Story 6.7 already added `estimateDaysToComplete(durationHours)` (`frontend/src/lib/utils/duration.ts:57-60`, `ceil(duration_hours/5)`, FR-19) and already renders it on the candidate card (`content-lookup-result-days-estimate`, `"≈ {N} days to complete (at 5 hrs/day)"`) whenever `duration_hours` is known. This story's AC3 (days-to-complete) is satisfied by that existing code — do not duplicate it. Verify it still renders correctly once Approve is live; do not touch `duration.ts`.
3. **`content_catalog.source` is a native Postgres enum (`content_source_enum`), not a CHECK constraint** (`backend/app/assignments/models.py:66`, `Enum("YOUTUBE", "MANUAL", name="content_source_enum")`) — the AC's "extended to include `UDEMY`" requires `ALTER TYPE content_source_enum ADD VALUE 'UDEMY'`, not a column-type rewrite. PostgreSQL 12+ (this project runs PG16) allows `ALTER TYPE ... ADD VALUE` inside a transaction block as long as the new value is never *used* (inserted/compared) in that same transaction — this migration's `upgrade()` only adds the value and does nothing else, so it is safe to run through Alembic's default transactional DDL exactly like migrations 001-008. Update the SQLAlchemy model's `Enum(...)` tuple to `Enum("YOUTUBE", "UDEMY", "MANUAL", name="content_source_enum")` in the same change, and extend `content/schemas.py::ContentResponse.source`'s `Literal["YOUTUBE", "MANUAL"]` to `Literal["YOUTUBE", "UDEMY", "MANUAL"]` (currently missed — Story 6.6 added `UDEMY` to `ContentLookupCandidate.source` but never touched `ContentResponse`, since nothing wrote a UDEMY row to `content_catalog` before this story).
4. **New columns are additive and both self-backfilling via their own defaults** (AC1): `attached_by UUID NULL REFERENCES employees(id)` (no `ondelete=` specified in the AC — mirror `Assignment.assigned_by`'s plain `ForeignKey("employees.id")`, no cascade action, not `OrgApiCredential.configured_by`'s `SET NULL` variant, since the AC doesn't ask for one) and `origin TEXT NOT NULL DEFAULT 'BATCH'`. The column `DEFAULT` handles every pre-existing row with zero explicit `UPDATE` statement — do not write one.
5. **Router file: new `content/admin_content_router.py`, not an existing router.** The endpoint's path is `/api/admin/content/attach` — a different prefix from both `skills/router.py` (`/api/admin/skills/...`, Story 6.6/6.7's sub-resource routes) and `content/router.py` (`/api/content`, employee-facing reads). Architecture spine's own Consistency Conventions table names this exact route under `/api/admin/...`. Mirror `content/admin_api_keys_router.py`'s existing shape exactly (own file, own prefix, `router = APIRouter(dependencies=[Depends(get_current_user)])`, thin routes calling straight into `content/service.py`) — this is the established "one module, multiple independently-mounted router files" pattern (progress/router.py + progress/my_assignments.py; content/router.py + content/admin_api_keys_router.py). Mount it in `backend/app/main.py`: `app.include_router(admin_content_router, prefix="/api/admin/content", tags=["admin-content"])`, alongside the existing `admin_api_keys_router` mount.
6. **No `description` field on the request.** The epics AC's embedding step says "computed for the title (+ description if the candidate has one)" — but trace every candidate type that can reach this endpoint (`ContentLookupCandidate` from Story 6.6, `ManualContentCandidate` from Story 6.7): neither carries a `description` field at all. There is currently no code path that could supply one. Per this codebase's established anti-premature-abstraction preference, do not add an unused `description` field to `AttachContentRequest` — embed from `title` alone (`_build_embedding_text(title, description=None)`, the existing helper already accepts `None`). Note this in Dev Notes as a deliberate omission, not an oversight, so it isn't "fixed" by review.
7. **`type` is never client-supplied — always hardcoded `"VIDEO"` in the service function**, per the AC's own wording ("content type inference from source is out of scope, default to VIDEO for YOUTUBE/UDEMY, MANUAL"). Do not add a `type` field to the request schema.
8. **`ContentResponse` is NOT extended with `attached_by`/`origin` fields in this story.** Nothing currently consumes either via the API — Story 6.9's reject endpoint (not this story) filters `origin = "ADMIN_LOOKUP"` server-side in its own repository query, never client-side; Story 6.10's Skills Card Grid only ever renders source/title/days-to-complete, never origin/attached_by. Adding unused response fields now would be exactly the kind of premature exposure this codebase avoids elsewhere (`ContentWithEmbedding` exists as a separate debug-only schema for the same reason). If a future story needs them exposed, add them then.
9. **Known, accepted gap, not something to fix here:** `content/service.py::manual_seed_content` (Story 2.3's CLI path) does not set `origin` explicitly, so any row it creates after this migration also silently backfills to `origin='BATCH'` via the column default — even though a CLI-seeded row isn't really "batch ingestion." The epics AC only specifies `origin` for *this* endpoint's own writes; changing `manual_seed_content` is out of scope. Leave it exactly as-is.
10. **Frontend: no panel to close, no Skills Card Grid to return to — adapt the UX spec's panel-level Approve-success behavior to this standalone component**, same kind of judgment call Story 6.7 already made adapting the Watch Modal spec to a component with no real page around it yet. The UX spec's "Approve success" state (04.1, Interactions & Behaviors / Content Lookup Panel Page States) says the panel closes immediately and a page-level toast confirms `"✓ Content approved for {Skill name}"` on the Skills Card Grid underneath. `ManualContentEntryForm` has no panel and no skill name (only a `skillId` prop) to interpolate. Add an optional `skillName?: string` prop (undefined by default — the dev demo page doesn't collect one); on Approve success, show the existing `Toast` primitive (`frontend/src/components/ui/toast.tsx`, already used elsewhere in this codebase, first added Story 3.5) with `` `✓ Content approved for ${skillName ?? 'this skill'}` ``, and put the card into an inline "Approved" state (disable further Approve clicks on that card, matches the spec's card leaving review once approved) rather than removing the card entirely (there's no grid to reveal underneath it). Story 6.10 will replace this whole component's placement inside the real panel and can wire a real `skillName` through then — write this prop so that hookup is a one-line change, not a rewrite.
11. **Frontend: Approve error state matches the UX spec exactly** — "Couldn't approve this — [Try again]" inline on the card (`content-lookup-btn-approve`'s sibling error state), same `FormErrorText` component already used for the Review-link error, card stays in its pre-approve state so the admin can retry.
12. **No UX addendum needed.** 04.1-skills-content-sourcing.md's `content-lookup-btn-approve`, `content-lookup-result-days-estimate`, and `skills-tab-toast` object IDs already fully specify the copy/behavior this story implements for the manual-entry candidate card — it gets "the identical View/Approve treatment as a searched result" per the spec's own words. Nothing here is undocumented.

## Acceptance Criteria

**Given** `content_catalog` (Story 2.1) has no `attached_by`/`origin` columns yet, and its `source` enum only allows `YOUTUBE`/`MANUAL` (Story 2.1/2.3)
**When** I write a new Alembic migration (009)
**Then** it adds, purely additively, no data loss to existing rows:
- `attached_by` (UUID, nullable, FK → `employees.id`) — nullable because every pre-existing row came from the batch job, not an Admin
- `origin` (text, not null, `DEFAULT 'BATCH'`) — every pre-existing row backfills to `'BATCH'` via the column default, correctly reflecting how they were actually populated; no explicit `UPDATE` needed since the default handles it
- `source`'s allowed values extended to include `UDEMY` via `ALTER TYPE content_source_enum ADD VALUE 'UDEMY'` (native Postgres enum, not a CHECK constraint — Scope Note 3)

**Given** the migration above has run
**When** I call `POST /api/admin/content/attach` with `{ skill_id, title, source, url, duration_hours }` as HR_ADMIN
**Then**:
- A `content_catalog` row is created: `skill_id`, `title`, `url`, `source` (`YOUTUBE`/`UDEMY`/`MANUAL`), `type: "VIDEO"` (always hardcoded, Scope Note 7), `origin: "ADMIN_LOOKUP"`, `attached_by: <my admin id>`, and (if `duration_hours` given) `content_metadata.duration_hours`
- An embedding is computed for the title via `core/embedding.py::embed_text()`, same as any other `content_catalog` write (Story 2.1/2.3 precedent) — an admin-sourced Content row is still eligible for future FR-3 semantic matching, not exempted from it
- The response is `201 Created` with the full `ContentResponse` (no raw embedding vector, per the existing convention; no `attached_by`/`origin` fields either, Scope Note 8)

**Given** the response includes `duration_hours`
**When** the client displays it
**Then** the estimate is computed **client-side** (`ceil(duration_hours / 5)`) per FR-19 — already implemented by Story 6.7's `estimateDaysToComplete` (Scope Note 2); this endpoint does not persist a computed "days to complete" value, only `duration_hours` itself

**Given** a candidate has no `duration_hours`
**When** it's approved
**Then** `content_metadata.duration_hours` is simply absent — the client omits the days-to-complete display entirely (never a guessed value, FR-19's consequence) — already correct behavior in the existing `estimateDaysToComplete`/display code

**Given** an EMPLOYEE session
**When** it calls `POST /api/admin/content/attach`
**Then** `403 Forbidden` (AD-6)

**Given** the Skill referenced by `skill_id` does not exist
**When** I call this endpoint
**Then** `404 Not Found` (mirrors Story 6.6/6.7's `{id}`-sub-resource 404 behavior, reusing `content/service.py::_not_found_skill()`)

**Given** `ManualContentEntryForm.tsx`'s candidate card, built by Story 6.7 with `[Approve]` visibly present but disabled (Scope Note 1)
**When** an HR Admin clicks `[Approve]` (`content-lookup-btn-approve`) on a reviewed manual-entry candidate
**Then** it calls this story's endpoint with `{ skill_id: skillId, title: candidate.title, source: candidate.source, url: candidate.url, duration_hours: candidate.duration_hours }`; on success the card shows an inline "Approved" state and a `Toast` confirms `` `✓ Content approved for ${skillName ?? 'this skill'}` `` (Scope Note 10); on failure an inline `FormErrorText` "Couldn't approve this — Try again" is shown and the card stays retryable (Scope Note 11)

**Out of Scope (this story):** re-validating a candidate's URL/metadata server-side beyond what Stories 6.6/6.7 already returned — this endpoint trusts the client-supplied candidate object; no separate server-side re-fetch. Also out of scope: the Skills Card Grid, the Content Lookup Panel shell, Story 6.6's search-result cards' own Approve wiring, and Story 6.9's Reject endpoint — all still `backlog`, Story 6.10/6.9's job.
