# Story 6.10: Skills Tab Frontend — Card Grid, Content Lookup, API Keys, Watch Modal

Status: done

## Story

As an **HR Admin**,
I want a single Skills tab where I can see every Skill, manage my/the org's credentials, and source or reject Content,
So that I have one place to close content gaps without waiting on anyone else, per UX spec 04.1.

## Scope Notes (read before starting)

1. **Real backend gap found while researching this story, not stated in the epics AC: there is no `GET /api/admin/skills` (list) endpoint today.** `backend/app/skills/router.py` only has `POST ""`, `PATCH "/{id}"`, `DELETE "/{id}"`, plus the two content sub-routes. The epics AC's own wording ("`GET` over Story 6.1's `skills.service.list_all_skills()`, extended to also return each Skill's current approved Content and `ever_assigned` status") describes an endpoint that does not exist yet — building it is this story's job, not a pre-existing dependency. `SkillResponse` already has `ever_assigned`; it does not carry a Skill's approved Content, and no route anywhere returns "all content for a skill" (`content.service.list_content_for_skill` exists but is never wired to a router).
2. **"Currently approved" means the most recent `content_catalog` row with `origin = "ADMIN_LOOKUP"` for that Skill — not any BATCH-ingested row.** Confirmed by reading `content/service.py::reject_content` (Story 6.9): it 404s on `origin != "ADMIN_LOOKUP"`, i.e. only admin-sourced rows are "approved"/rejectable in this epic's sense. A Skill can independently have BATCH-ingested rows from Epic 2's batch job (used for the Employee-facing AI match, a different surface, PRD §4.2) — those are never shown as this Skill Tab's "approved" link. `ingested_at` doubles as "approved at" (no separate column) since `attach_content` sets it at write time.
3. **New backend pieces, composed the same way Story 6.6/6.7's sub-routes already are (`skills/router.py` calling into `content/service.py` for a Skill sub-resource whose real logic needs Content-module data) — not a violation of AD-8's "Content depends on Skills, never back" since only the router layer composes across modules, `skills/service.py` itself stays untouched:**
   - `content/schemas.py`: new `SkillWithContentResponse` — `id: UUID`, `name: str`, `description: str | None`, `ever_assigned: bool`, `approved_content: ContentResponse | None`.
   - `content/repository.py`: new `list_admin_lookup_content_for_skills(db, skill_ids: list[UUID]) -> list[ContentCatalog]` — one query, `WHERE skill_id IN (...) AND origin = 'ADMIN_LOOKUP'`, `ORDER BY skill_id, ingested_at, id` (ascending — the caller picks the *last* row per `skill_id`, i.e. most recent, avoiding N+1 queries across however many Skills exist).
   - `content/service.py`: new `async def list_skills_with_content(db, *, current_user) -> list[SkillWithContentResponse]` — `require_hr_admin(current_user)` first (Scope Note 4), then `skills_service.list_all_skills(db)`, then the bulk query above, group by `skill_id` keeping the last (most recent) row, assemble the response list preserving `list_all_skills`'s own order.
   - `skills/router.py`: new `@router.get("", response_model=list[SkillWithContentResponse])` calling `content_service.list_skills_with_content(session, current_user=current_user)` — same file/composition pattern as the existing `content_lookup_route`/`content_manual_route`.
4. **This new list route must be HR_ADMIN-gated (403 for EMPLOYEE), even though the epics AC's literal text for Story 6.10's page-load AC doesn't spell out an explicit "given EMPLOYEE session" clause the way most other Epic 6 endpoints' ACs do.** AD-6's blanket rule ("every endpoint in this epic is HR_ADMIN-gated") and the UX spec's own framing (`/skills`, "Internal (HR Admin only, FR-14)") both point the same direction, and every sibling endpoint in this router/module already enforces this — an unauthenticated read hole here would be the one inconsistent exception. Added as an explicit AC below (AC1a) and a router test, following the exact 401/403 pattern every other route in this file already uses.
5. **Frontend reuse — do not rebuild any of these, they already exist and match the UX spec's object IDs exactly:**
   - `ApiKeysModal` (`frontend/src/features/admin/ApiKeysModal.tsx`, Story 6.5) — the entire "Manage API Keys" modal. Render it directly; wire the toolbar's "Manage API Keys" button to `open`.
   - `ContentPreviewModal` (`frontend/src/features/admin/ContentPreviewModal.tsx`, Story 6.7) — the entire "Watch Modal". Every content link on this page (a Skill card's approved link, a search result's `[View]`, a manual candidate's `[View]`, the Currently-Approved card's `[View]`) opens this same instance with that link's `{title, source, url, durationHours}`.
   - `CurrentlyApprovedContent` (`frontend/src/features/admin/CurrentlyApprovedContent.tsx`, Story 6.9) — the entire "Currently Approved" section inside the Content Lookup Panel. Render it directly when `skill.approved_content` is non-null, passing its real fields + `skillName` + an `onRejected` that clears local state so the section disappears and the panel stays open (UX-DR32).
   - `ManualContentEntryForm` (`frontend/src/features/admin/ManualContentEntryForm.tsx`, Story 6.7/6.8) — the entire "Paste a link" tab. Needs one small **additive** change (Task 7): an optional `onApproved?: () => void` prop, called right after a successful `attachContent` so the panel can close immediately per UX-DR29 (today it only sets its own internal `approved`/`toastMessage` state, which is correct for its standalone dev-demo usage but insufficient once a real panel needs to close and hand off to a page-level toast).
   - `estimateDaysToComplete`/`parseDurationToHours` (`frontend/src/lib/utils/duration.ts`) — reuse as-is for the Search tab's new result cards.
   - `Dialog`, `Card`/`CardContent`, `Button`, `Input`, `Label`, `FormErrorText`, `Toast` (`frontend/src/components/ui/*`) — the established primitives every admin modal/form in this codebase is built on; use them for every new modal/card in this story, not new markup patterns.
6. **New frontend pieces this story actually builds** (nothing above covers these):
   - `frontend/src/lib/api/skillsApi.ts` — `listSkillsWithContent()` (`GET /api/admin/skills`), `createSkill({name, description})` (`POST /api/admin/skills`), `updateSkill(skillId, {name?, description?})` (`PATCH /api/admin/skills/{id}`), `deleteSkill(skillId)` (`DELETE /api/admin/skills/{id}`) — same one-function-per-endpoint, snake_case-field convention as every other file in `frontend/src/lib/api/`.
   - `frontend/src/lib/api/adminContentApi.ts` — add `searchContentForSkill(skillId, query)` (`POST /api/admin/skills/{id}/content-lookup`, Story 6.6) plus its `ContentLookupCandidate`/`ContentLookupSourceError`/`ContentLookupResponse` types (mirroring `content/schemas.py` field-for-field) — the one Story 6.6 endpoint that, per the frontend-conventions research for this story, has **no** existing client function anywhere in the repo. Placed in this file (not the new `skillsApi.ts`) to match `reviewManualContent`'s existing precedent in the same file for another Skill-sub-resource route.
   - `frontend/src/features/admin/SkillCard.tsx` — one Skills Card Grid card (UX-DR25/26).
   - `frontend/src/features/admin/NewSkillModal.tsx` — the "New Skill" panel (create-only, FR-20, UX-DR31).
   - `frontend/src/features/admin/DeleteSkillModal.tsx` — the delete-confirmation modal (FR-22, UX-DR32's Delete-side).
   - `frontend/src/features/admin/ContentLookupPanel.tsx` — the composite panel: edit-name/description fields, `CurrentlyApprovedContent` slot, Search/Paste-a-link tabs, the Search tab's own result-card rendering (built fresh — no existing component for this), YouTube/Udemy toggle-with-"Add a key" gating.
   - `frontend/src/pages/hr/SkillsPage.tsx` — the page: header (mirrors `Dashboard.tsx`'s header markup, "Skills" nav item active instead of "Dashboard" — no shared header component exists in this codebase yet, so this follows the same per-page-inline convention `Dashboard.tsx` already uses rather than introducing one), toolbar, grid, and all the modals above wired together.
7. **Skill Card's "one approved link, never a list" rule (UX-DR25) is already enforced server-side** by Scope Note 3's repository query picking exactly one (the most recent) row — the frontend renders whatever `approved_content` the API gives it, no client-side "pick the latest of several" logic needed.
8. **Locked/assigned Skills genuinely have no entry point into the Content Lookup Panel on this page — this is UX-DR33's explicitly-flagged, intentionally-unresolved gap (PRD Open Question 17), not an oversight to "fix" during implementation.** A locked card shows only the 🔒 "Locked — assigned to an Employee" text (UX-DR26) in place of Edit/Delete; do not add a Find-Content button or any other path into the panel for these cards.
9. **YouTube/Udemy search toggle checkboxes are a client-side display filter, not a request parameter — `ContentLookupRequest` (Story 6.6) has only `query: str`, no source-selection field.** The panel always calls `searchContentForSkill(skillId, query)` once per Search click (the backend itself always tries every source it has a credential for and reports the rest as per-source `errors`); the checkboxes control which of the two returned result groups are rendered, and are force-unchecked+disabled (with the "Add a key" inline prompt) whenever `GET /api/admin/api-keys` reports `configured: false` for that source. Fetch API-key status once when the panel opens (reuse `getApiKeysStatus` from `frontend/src/lib/api/adminApiKeysApi.ts`, already built) — do not add a source param to the backend request schema; that would be scope creep into Story 6.6's already-shipped, already-reviewed contract.
10. **"Approving a candidate closes the panel immediately" (UX-DR29) applies uniformly across all three approve paths on this page** — a Search-tab result card's `[Approve]`, the Paste-a-link tab's `[Approve]` (via `ManualContentEntryForm`'s new `onApproved` hook, Scope Note 5), and (implicitly) re-approving after a Reject. `ContentLookupPanel` owns one `handleApproved()` that: calls `onClose()` immediately, then calls a parent-supplied `onApproved(skillId, skillName)` so `SkillsPage` can show its own page-level `Toast` (`✓ Content approved for {Skill name}`) and refetch the grid. The Search tab's own result cards are built fresh in `ContentLookupPanel` (call `attachContent` directly, already exported from `adminContentApi.ts`) since no existing component renders a Story 6.6 candidate.
11. **New Skill → Content Lookup hand-off (UX-DR31) and duplicate-name "Use existing skill" (both the New Skill panel's and — separately, no redirect offered there per the UX spec — the Content Lookup Panel's own edit-name save) are two different 409-handling behaviors, do not conflate them:** `NewSkillModal`'s 409 shows "A skill named '{name}' already exists. [Use existing skill]" where clicking the link closes `NewSkillModal` and opens `ContentLookupPanel` for the **existing** Skill (the `existing_skill.id`/`name` the 409 body already carries, per `skills/service.py::_conflict`'s `extra` payload) with the entered search term still pre-filled. `ContentLookupPanel`'s own edit-mode rename-conflict shows only "A skill named '{name}' already exists." with **no** redirect link (the rename 409 has no `extra` payload at all — `_rename_conflict` deliberately omits it, confirmed by reading `skills/service.py`).
12. **Out of scope, explicitly per the epics AC's own "Out of Scope" note:** full production-grade Loading/Empty/Error polish beyond this codebase's established rigor (Story 5.1/5.7's pattern is the bar — a loading state, an empty-grid state, a retryable error banner — not the mock's bare happy-path). Also out of scope: resolving PRD Open Question 17/UX-DR33 (Scope Note 8), and any change to Story 6.6's `ContentLookupRequest` schema (Scope Note 9).

## Acceptance Criteria

**AC1 (page load, grid).** **Given** UX spec `04.1-skills-content-sourcing.md`, Section "Main Content: Skills Card Grid" **When** the Skills tab (`/skills`) loads **Then** it renders one card per Skill (`GET /api/admin/skills`, Scope Note 3), showing: Skill name, an "✓ Approved"/"⚠ None yet" badge, exactly **one** approved link if any exists (the most recently admin-approved — UX-DR25, Scope Note 2), and a utility row — Edit (✎) + Delete (🗑) icons for `ever_assigned = false` Skills, or a 🔒 "Locked — assigned to an Employee" indicator for `ever_assigned = true` Skills (UX-DR26).

**AC1a (list endpoint gating, Scope Note 4).** **Given** an EMPLOYEE session **When** it calls `GET /api/admin/skills` **Then** `403 Forbidden` (AD-6). **Given** no session **Then** `401`.

**AC2 (create).** **Given** the toolbar **When** I click `[+ New Skill]` **Then** a modal opens (name required, description optional) calling Story 6.2's create endpoint; on success it closes and the Content Lookup panel opens automatically for the new Skill with the entered name pre-filled as the search term (UX-DR31); on a `409` duplicate response, an inline notice offers "Use existing skill" (opens Content Lookup for the existing one instead, Scope Note 11).

**AC3 (edit entry point).** **Given** an unassigned Skill's card **When** I click ✎ Edit **Then** the Content Lookup panel opens in edit mode: editable Name/Description fields (calling Story 6.3's `PATCH` on save, panel stays open afterward) plus everything the panel offers otherwise — this is the **only** entry point into content-sourcing for an unassigned Skill; 🗑 Delete opens a confirmation modal (Story 6.3's `DELETE`, requires explicit confirm, page-level toast on success).

**AC4 (currently approved).** **Given** the Content Lookup panel (any entry) **When** it opens for a Skill that already has an approved Content link **Then** a "Currently Approved" section renders above the search tabs (source, title as a button opening the Watch Modal, days-to-complete if known) with a "Reject" button calling Story 6.9's endpoint (no confirmation; on success the section clears, the panel **stays open**, a page-level toast confirms) — UX-DR32.

**AC5 (search).** **Given** the panel's Search tab **When** I toggle YouTube/Udemy (each disabled with an inline "Add a key" prompt if `GET /api/admin/api-keys` shows `configured: false` for that source, Scope Note 9) and submit **Then** it calls Story 6.6's lookup endpoint and renders result cards grouped by source, each labeled "Search Results" (never "Recommended," UX-DR27), with duration + days-to-complete (FR-19) shown only when known (UX-DR28), a `[View]` button opening the Watch Modal, and an `[Approve]` button calling Story 6.8's attach endpoint.

**AC6 (manual entry).** **Given** the panel's "Paste a link" tab **When** I fill in URL/Title/optional-Duration and click "Review link" **Then** it calls Story 6.7's manual-entry endpoint (via `ManualContentEntryForm`) and renders the resulting candidate with the identical View/Approve treatment as a searched result.

**AC7 (approve closes panel).** **Given** any `[Approve]` click (search result, manual entry, or otherwise) **When** the attach call succeeds **Then** the Content Lookup panel **closes immediately** (UX-DR29), the Skills Card Grid re-renders with that Skill's card now showing the new approved link, and a page-level toast confirms ("✓ Content approved for {Skill name}").

**AC8 (watch modal).** **Given** any content link anywhere on this page (a search/manual/currently-approved candidate's `[View]`, or an already-approved link on a Skill card) **When** clicked **Then** it opens the Watch Modal, in-app, with a close control — embeds via `<iframe src="https://www.youtube.com/embed/{id}">` for a recognizable YouTube link, otherwise shows an explicit "preview not available" state with an "Open in new tab" fallback (UX-DR30) — never a bare `target="_blank"` redirect.

**AC9 (API keys).** **Given** the toolbar's "Manage API Keys" button **When** clicked **Then** the existing `ApiKeysModal` opens (Story 6.5, reused as-is per Scope Note 5).

**AC10 (locked skills, gap).** **Given** UX spec 04.1's explicitly-flagged gap **When** a Skill has `ever_assigned = true` **Then** its card has **no** control that opens the Content Lookup panel (Scope Note 8; PRD Open Question 17 stays open).

**Out of Scope (this story):** see Scope Note 12.
