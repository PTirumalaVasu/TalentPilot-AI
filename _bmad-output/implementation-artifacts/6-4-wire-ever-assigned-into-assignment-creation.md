# Story 6.4: Wire `ever_assigned` Into Assignment Creation (AD-11 point 3)

Status: done

## Story

As a **developer**,
I want `assignments/`'s Assignment-creation flow to set the target Skill's `ever_assigned` flag,
so that Story 6.3's permanent lock actually engages the first time a Skill is assigned — without `skills/` ever needing to query `assignments` directly.

## Scope Notes (read before starting)

1. **This closes a known, already-shipped gap.** Story 6.3's code review (2026-09-09, all 3 review layers independently) found that `POST /api/assignments` creates Assignments today with nothing calling a flag-setter — `mark_ever_assigned` doesn't exist yet. The user explicitly deferred the fix to this story rather than blocking 6.3 on it (`deferred-work.md`, "Deferred from: code review of 6-3..."). This story is that fix. Once done, note in the story's Dev Notes that the deferred-work.md entry is resolved.
2. **No new module, no new endpoint, no new UI.** `skills/` and `assignments/` both already exist (Story 6.1–6.3). This story adds one repository function, one service function, and one call site. The Skills tab's 🔒 lock indicator (`_bmad-output/C-UX-Scenarios/04-ritas-content-curation/04.1-skills-content-sourcing/04.1-skills-content-sourcing.md`) already renders off `SkillResponse.ever_assigned` (Story 6.1/6.2) — this story is what makes that flag start reflecting reality; no frontend file changes.
3. **`skills.service.mark_ever_assigned(skill_id)` does not exist — create it.** Mirror the existing `content.service.match_content_for_skill(db, skill_id)` shape exactly (`backend/app/content/service.py:236`): a plain `(db, id)` signature, **no `current_user` parameter, no `require_hr_admin` check inside it**. Auth is already enforced once, at `create_assignment_service`'s own entry point (`require_hr_admin(current_user)`, `backend/app/assignments/service.py:91`) — this is a same-request internal call, not a new externally-reachable capability. This is also the same cross-module dependency shape `assignments/` already has on `content/` for FR-1/FR-2 (AD-8) — confirmed by the epic text itself as "not a new architectural pattern."
4. **The write must be idempotent by construction, not by an if-check in Python.** AC2 requires that calling `mark_ever_assigned` on an already-`true` Skill is a no-op — no error. Do this with a single conditional `UPDATE ... WHERE id = :skill_id AND ever_assigned = false` (Core-level statement, same style as `skills/repository.py::delete_skill`) rather than a `SELECT`-then-maybe-`UPDATE` round trip. Zero rows matching (already `true`, or the id doesn't exist) is a normal, silent success — never raise.
5. **The hard part: a failure in the flag-set call must never lose the Assignment.** AC1's own wording is explicit: the flag-set call happens "in the same request but not the same DB transaction" as the Assignment insert — "if the flag-set call fails, the Assignment itself must not be rolled back or lost; log and continue." This codebase commits once per request (`core/db.py::get_db`: commits after the route handler returns, rolls back the *entire* session on any exception that escapes it) and `create_assignment` only `flush()`s, not commits (`assignments/repository.py:94`) — so a bare, unguarded `await mark_ever_assigned(...)` that raises would propagate out of `create_assignment_service`, hit `get_db`'s `except Exception: rollback`, and take the already-flushed-but-uncommitted Assignment down with it. **Required pattern:** wrap the call in `async with session.begin_nested():` (a SQL SAVEPOINT) inside a `try/except`, so a failure inside the nested block only rolls back to the savepoint — leaving the outer transaction (and the Assignment already flushed onto it) intact and still committable — then `logger.exception(...)` and continue; do not re-raise. This is a new pattern for this codebase (no prior `begin_nested()` usage) — introduced specifically because this is the first place a "hard-dependency, secondary write must not endanger the primary write" requirement has come up.
6. **Call site and ordering:** in `assignments/service.py::create_assignment_service` (`backend/app/assignments/service.py:83-110`), call `mark_ever_assigned` **after** `create_assignment(...)` returns (i.e. after the Assignment is flushed) and **before** building/returning the `AssignmentResponse`. Do not gate it on whether `content_id` was resolved — it fires for every successful Assignment creation regardless of content-matching outcome.
7. **Import direction:** `assignments/service.py` gains `from app.skills.service import mark_ever_assigned` — same direction/shape as its existing `from app.content.service import match_content_for_skill` import already sitting right above where the new import goes (`backend/app/assignments/service.py:39`). Do not have `skills/` import anything from `assignments/` (AD-1/AD-8 direction stays one-way).
8. **Do not touch `skills/router.py` or `skills/schemas.py`.** `mark_ever_assigned` is a service-to-service call only, never exposed via any HTTP route.
9. **Test with a live-DB private-engine session, matching `test_assignments_service.py`'s existing pattern exactly** (`backend/tests/test_assignments_service.py:1-34`, `_seeded_session` context manager, `pytestmark = pytest.mark.asyncio(loop_scope="module")`) — do not use `conftest.py`'s shared `db_session` fixture (documented `drop_all()`-wipes-the-dev-DB landmine, `deferred-work.md`). Seeded skill IDs available: `SKILL_DATA_VIZ_ID`, `SKILL_SALESFORCE_ID`, `SKILL_PYTHON_ID`, `SKILL_SQL_ID`, `SKILL_COMMUNICATION_ID` (`backend/app/core/seeds.py:14-18`) — all seed with `ever_assigned` defaulting to `False` (no seeded Assignments touch them).
10. **To test the failure-isolation behavior (Scope Note 5), monkeypatch `app.assignments.service.mark_ever_assigned`** (the name as imported into that module, not `app.skills.service.mark_ever_assigned`) to an async function that raises, then assert `create_assignment_service` still returns a normal `AssignmentResponse` and the Assignment row is actually queryable within the same session afterward (e.g. via `find_existing_assignment`) — proving the outer transaction survived.

## Acceptance Criteria

**Given** `assignments/`'s existing `create_assignment` service method (Story 3.1, extended by Story 3.4)
**When** an Assignment is successfully created for `(employee_id, skill_id)`
**Then** it calls `skills.service.mark_ever_assigned(skill_id)` — a `skills/`-owned write (AD-1: `assignments/` never writes the `skills` table directly) — after the Assignment insert is flushed, in the same request but not the same DB transaction as a hard dependency (if the flag-set call fails, the Assignment itself must not be rolled back or lost; log and continue — a missed flag-set is a data-quality issue to reconcile, not grounds to lose a real Assignment, AR-13)

**Given** `mark_ever_assigned(skill_id)` is called for a Skill that already has `ever_assigned = true`
**When** the flag-set executes
**Then** it's a no-op (idempotent — re-assigning an already-assigned Skill, or a second intentional Assignment per FR-1, does not error)

**Given** this dependency direction
**When** reviewing `assignments/`'s existing module dependencies
**Then** this is the same shape as `assignments/`'s pre-existing dependency on `content/` for FR-1/FR-2's content lookup (AD-8) — confirmed here, not a new architectural pattern, just one more peer-module call in the same direction

### Review Findings

`bmad-code-review` (2026-09-09, 3 parallel adversarial layers — Blind Hunter, Edge Case Hunter, Acceptance Auditor; both Blind Hunter and Edge Case Hunter stalled on their first attempt and were successfully retried). 0 decision-needed, 3 patches, 3 deferred, 6 dismissed.

- [x] [Review][Patch] The `except Exception: logger.exception(...)` around the SAVEPOINT doesn't verify the session is actually still usable afterward, so the code comment's claim ("the Assignment itself must not be rolled back or lost") isn't fully backed for a connection-fatal failure inside the SAVEPOINT — if the underlying connection is invalidated (not just a clean constraint violation), the session could still be broken when `core/db.py::get_db`'s final commit runs, losing the Assignment anyway. Empirically verified the *common* case (a real `IntegrityError` inside `begin_nested()`) leaves `session.is_active == True` and the outer transaction commits cleanly — so the fix is to explicitly re-raise when `session.is_active` is `False` after the catch, converting a genuinely unrecoverable session into a clean request failure instead of a silently-corrupted one, while still swallowing the realistic/recoverable failure class. Fixed: added the `if not session.is_active: raise` guard. [backend/app/assignments/service.py:107-118]
- [x] [Review][Patch] `test_mark_ever_assigned_failure_does_not_lose_the_assignment` only monkeypatches a pure-Python `RuntimeError` stand-in — it never exercises a real DB-level error occurring *inside* the SAVEPOINT, which is the actual failure mode this design exists to protect against (verified separately, outside the test suite, that a real `IntegrityError` inside `begin_nested()` is correctly isolated — but nothing in the test suite proves this). Fixed: added `test_real_db_error_inside_savepoint_does_not_lose_the_assignment`, which patches `mark_ever_assigned` to attempt a genuine constraint-violating `UPDATE` (`skills.name = NULL`) and confirms the Assignment still commits and `session.is_active` stays `True`. [backend/tests/test_assignments_service.py]
- [x] [Review][Patch] `skills/repository.py::mark_ever_assigned`'s trailing `await db.flush()` is a no-op — the preceding statement is a Core-level `db.execute(update(...))`, which is already sent to the DB synchronously; there's no pending ORM-tracked object for `flush()` to synchronize (unlike `update_skill`, whose pattern this was copied from, which does mutate a loaded ORM object). Harmless but misleading about what's actually needed for correctness. Fixed: removed the call, documented why in the docstring. [backend/app/skills/repository.py:112-118]
- [x] [Review][Defer] Another transaction reading the target Skill before this request's own commit still sees `ever_assigned = False` — the "permanent lock" isn't durable until the whole request commits. Inherent to this codebase's single-commit-per-request model (`core/db.py::get_db`), true of every write in every endpoint here, not something this diff introduces or could fix without redesigning that shared architecture. — deferred, pre-existing, systemic [backend/app/assignments/service.py, backend/app/core/db.py]
- [x] [Review][Defer] Two concurrent `create_assignment_service` calls against the same never-before-assigned `skill_id` could have the second request's conditional `UPDATE` block on a Postgres row lock until the first request's transaction commits — a liveness/latency characteristic, not an incorrectness one. Matches the exact class of gap already logged from Story 6.3's review ("No row-level locking/TOCTOU guard... very low likelihood for this internal, admin-only, low-concurrency tool"). — deferred, matches existing accepted precedent [backend/app/skills/repository.py:103-115]
- [x] [Review][Defer] A Skill hard-deleted (Story 6.3's `DELETE /api/admin/skills/{id}`) concurrently with an in-flight `create_assignment_service` call for it. Reasoned through Postgres's actual concurrency semantics: `assignments.skill_id`'s FK is `RESTRICT` (unchanged by this diff) and the referencing `INSERT` takes a `FOR KEY SHARE` lock on the Skill row, so a concurrent delete either blocks-then-fails against a real referencing row, or (if the delete wins the race) the Assignment's own `INSERT` fails with an FK violation *before* `mark_ever_assigned` is ever reached — an existing, unrelated gap (`create_assignment_service` has no `IntegrityError` handling for this) that predates and is independent of this story. — deferred, pre-existing, unrelated to this diff's own logic [backend/app/assignments/service.py, backend/app/skills/repository.py::delete_skill]

**Dismissed** (noise, false positive, or already handled elsewhere): `skills.service.mark_ever_assigned` having no internal auth check, relying on the caller (`require_hr_admin` in `create_assignment_service`) — this is the exact same shape as the established precedent it's explicitly documented to mirror, `content.service.match_content_for_skill`, which also takes no `current_user` and performs no auth check; the "compensating control" (a reconciliation job) the code comment is accused of falsely implying doesn't exist — the comment classifies a missed flag-set as "a data-quality issue to reconcile," which describes the failure's nature, not a claim that automated tooling exists, and no AC requires one;
