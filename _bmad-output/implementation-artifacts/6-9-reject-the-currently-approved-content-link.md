# Story 6.9: Reject the Currently Approved Content Link (FR-23)

Status: done

## Story

As an **HR Admin**,
I want to remove a Skill's currently-approved Content link outright, independent of approving a replacement,
So that I can clear a bad or outdated link even if I don't have a replacement lined up yet.

## Scope Notes (read before starting)

1. **This story is API + a frontend slice pulled forward from Story 6.10, by explicit user instruction** ("start development api and ui for the story 6-9 ... refer the ux design if required") — same category of deviation Stories 6.7 and 6.8 already made from Story 6.6's API-only precedent. Story 6.10 owns the *whole* Skills tab (Card Grid, Content Lookup Panel shell, Edit/Delete, Search-tab Approve wiring). **Unlike Story 6.8 — which only had to wire an already-existing disabled `[Approve]` button — Story 6.10 has not yet built ANY "Currently Approved" UI.** There is nothing to wire; this story builds a new, standalone `CurrentlyApprovedContent` component from the UX spec, following the exact same "component ahead of its real panel" precedent Story 6.5 (`ApiKeysModal`) and Story 6.7 (`ManualContentEntryForm`/`ContentPreviewModal`) already established, each exercised via its own `/dev/*-demo` route. Do not build the Skills Card Grid, the Content Lookup Panel shell, Edit-mode Save-name wiring, or Search-tab/Approve wiring — those stay Story 6.10's job, still `backlog`.
2. **The endpoint is a flat resource route with no `skill_id` anywhere in it — `DELETE /api/admin/content/{content_id}/reject`** — confirmed both by the epics AC's own literal text (epics.md line 2378) and the architecture spine's Consistency Conventions table, which names this exact route. The epics AC's 404 condition ("`content_id` does not exist, or exists but does not belong to the given Skill / was not admin-sourced") is worded as if a `skill_id` were part of the request, but none is — there is no "given Skill" anywhere in this endpoint's actual signature. Read literally, the only two things checkable from `content_id` alone are: (a) does a row exist, and (b) is `origin == "ADMIN_LOOKUP"`. Implement the 404 condition as exactly those two checks (mirrors `content/service.py::_not_found_skill()`'s existing "no distinction leaked" pattern, applied here to content instead of skill) — do not invent a `skill_id` request parameter that no other part of the epics/architecture ever names.
3. **A real, undocumented system gap, found by reading the actual schema (not stated in the epics AC) — must be fixed for the feature to work end-to-end:** `assignments.content_id`'s FK (`backend/alembic/versions/001_initial_schema.py:104`, `sa.ForeignKeyConstraint(['content_id'], ['content_catalog.id'])`) has no `ondelete=` action, meaning it defaults to Postgres's `NO ACTION` (behaves like `RESTRICT`). If any `Assignment` row's `content_id` currently points at the `content_catalog` row being rejected — a real, reachable state: `match_content_for_skill` (Story 2.4) can pick an admin-attached (`origin="ADMIN_LOOKUP"`) row as an Assignment's best match at assignment-creation time — a hard `DELETE` of that row raises a Postgres `IntegrityError` (surfaces as an unhandled 500) instead of the clean `204` the AC promises. `assignments.content_id` is already `nullable=True` and every part of this codebase that reads it (dashboard, Content Discovery) already handles a `None` value (it starts `None` whenever `match_content_for_skill` finds nothing) — so the correct, minimal fix is a new migration (010) giving `assignments.content_id`'s FK `ondelete='SET NULL'`, mirroring migration 007's identical precedent for `content_catalog.skill_id → skills.id`. This is a pure DB-level referential action — `content/` never writes to the `assignments` table directly (AD-1/AD-8 stay intact, same reasoning migration 007's own docstring already documents for the analogous case). **Verify the live constraint's actual name before writing the migration** (`\d assignments` against the running dev Postgres container, or `SELECT conname FROM pg_constraint WHERE conrelid = 'assignments'::regclass AND contype = 'f'`) — it is unnamed in `001_initial_schema.py`, so Postgres will have assigned its own default name (likely `assignments_content_id_fkey`, following the same `<table>_<column>_fkey` pattern migration 007 already confirmed for `content_catalog_skill_id_fkey`, but confirm rather than assume).
4. **Router: new route in the existing `content/admin_content_router.py` (Story 6.8's file), not a new router file.** `DELETE /{content_id}/reject`, `status_code=204`, no response body. Same file, same `/api/admin/content` prefix already mounted in `main.py` — no new `include_router` call needed.
5. **Service: `reject_content(db, *, current_user, content_id) -> None`**, mirroring `skills/service.py::delete_skill_service`'s exact fetch-then-delete shape (`backend/app/skills/service.py:224-237`): `require_hr_admin` first, fetch via `repository.get_content_by_id` (already exists, no new repository read needed), 404 if missing or `origin != "ADMIN_LOOKUP"` (Scope Note 2), then `repository.delete_content` + `db.commit()`. Not gated by the Skill's `ever_assigned` at all — this function never looks at the Skill row or its lock flag (AD-11 point 5, PRD FR-23's explicit "not gated by assignment/lock status" consequence). Add a new `_not_found_content()` helper next to the existing `_not_found_skill()` (same file, same one-liner shape) rather than reusing `_not_found_skill()` for a content-not-found condition — they are different resources with different error messages, matching this module's established "small, explicit per-condition helper" convention.
6. **Repository: new `delete_content(db, content_id) -> None`**, mirroring `skills/repository.py::delete_skill`'s exact reasoning (`backend/app/skills/repository.py:89-100`) — issue a Core-level `delete(ContentCatalog).where(ContentCatalog.id == content_id)`, not `db.delete(<ORM object>)`, so the ORM's unit-of-work never loads the `assignments`/`skill` relationships. `get_content_by_id` (used for the existence/origin check) already exists in `repository.py` — no new read function needed, only the new delete.
7. **No response body on success (`204 No Content`)** — do not add a response schema; the router function returns `None` with `status_code=status.HTTP_204_NO_CONTENT`, matching FastAPI's standard no-body-response shape (no existing precedent for a 204 in this codebase yet — `DELETE /api/admin/skills/{id}` from Story 6.3 is the closest sibling, confirm it also returns 204/no body before writing this route).
8. **Frontend: new `frontend/src/features/admin/CurrentlyApprovedContent.tsx`**, built directly from UX spec `04.1-skills-content-sourcing.md`'s `content-lookup-current-approved` / `content-lookup-btn-reject` object IDs (lines 190-191) and the Interactions & Behaviors table's exact page-state copy (lines 378-383): a card — green-tinted (`border-green-200 bg-green-50` on the existing `Card` primitive's `className` override, `Card`/`CardContent` already accept one, `frontend/src/components/ui/card.tsx:4-8`) — showing source, title, days-to-complete (reuse `estimateDaysToComplete` from `frontend/src/lib/utils/duration.ts:57-60`, already built and untouched by this story per Story 6.8's identical precedent), a `[View]` button opening `ContentPreviewModal` (reuse as-is, `frontend/src/features/admin/ContentPreviewModal.tsx`, first built Story 6.7), a `[Reject]` button (`content-lookup-btn-reject`), and the exact helper text "Approving a new link below will also replace this." ## Acceptance Criteria

**Given** a Skill has an approved `content_catalog` row with `origin = "ADMIN_LOOKUP"`
**When** I call `DELETE /api/admin/content/{content_id}/reject` as HR_ADMIN
**Then** that `content_catalog` row is **hard deleted** (no soft-delete/audit columns, `[ASSUMPTION]` per PRD FR-23's consequence — consistent with Story 6.3's Skill-deletion reasoning: admin-sourced Content carries lighter audit weight than Assignment/watch-progress history) and `204 No Content` is returned

**Given** rejecting a Content row
**When** it succeeds
**Then** no confirmation step is required (unlike Story 6.3's Skill deletion) — this is deliberately lower-friction, matching FR-23's "no confirmation step" consequence, since it's immediately reversible in spirit (the Admin can search and approve something else right away)

**Given** this endpoint
**When** called for a Skill regardless of its `ever_assigned` value
**Then** it succeeds the same way either way — **not gated by Skill assignment/lock status** (AD-11 point 5, PRD FR-23's consequence) — the permanent lock (Story 6.3) applies only to the Skill's own identity (name/description/existence), never to its Content

**Given** the `content_id` does not exist, or exists but was not admin-sourced (`origin != "ADMIN_LOOKUP"`)
**When** the request is made
**Then** `404 Not Found` — no distinction leaked between "doesn't exist" and "not admin-sourced" (same uniform-403/404 pattern already established for `assignments/`'s scoped lookups, Story 1.3; Scope Note 2 on this route's actual, skill-less signature)

**Given** an EMPLOYEE session
**When** it calls this endpoint
**Then** `403 Forbidden` (AD-6)

**Given** the `content_catalog` row being rejected is currently referenced by an existing `Assignment.content_id`
**When** the hard delete runs
**Then** it still succeeds with `204 No Content` — the referencing Assignment's `content_id` is set to `NULL` by the database's own `ON DELETE SET NULL` referential action (migration 010, Scope Note 3), not left to fail with an unhandled `IntegrityError`; this is a real system-integrity requirement discovered by reading the existing schema, not explicit epics text, but necessary for this story's own stated `204` promise to hold in every reachable state
