# Epic 9 Retrospective: Skill Assignment Dashboard

Run **out of order**: Epic 9 finished on 2026-09-14, but this retrospective is happening on 2026-09-15, after a full day of Epic 10 planning and mockup work already occurred. That timing is unusual but not accidental — it means Part 2 of this retro isn't speculating about a hypothetical next epic. Epic 10 ("Post-MVP Admin & Roster Refinements") is already fully authored: 16 stories, `prd.md` FR-34–FR-43, all `backlog`. Several of those stories directly touch — and in one case substantially reverse — work this epic just shipped. That gives this retrospective unusually concrete material for its forward-looking half.

## Epic Summary

**Epic 9 — Skill Assignment Dashboard:** 5/5 stories done (9.1–9.5). New org-wide stats/Assignment-Progress endpoint, an Employee Segmentation endpoint (On Track / In Progress / Needs Attention), a new `/dashboard` landing page HR Admins see on login, a Needs Attention popover with drill-down, and a left-nav amendment giving the pre-existing full grid its own "Skill Assignments" entry. Realizes FR-31 through FR-33 and amends FR-29.

**Split:** 2 backend stories (9.1, 9.2 — `dashboard/` module, read-composition only, zero new tables per AR-26), 3 frontend stories (9.3, 9.4, 9.5).

**Velocity:** planned 2026-09-13, all 5 stories implemented and reviewed by 2026-09-14 — two days, in line with Epic 6/7's pace as this project's fastest epics.

**Quality:** All 5 stories received a full 3-layer adversarial code review (Blind Hunter / Edge Case Hunter / Acceptance Auditor). **All 5 reviews found and fixed something real** — this project's review streak is now unbroken across every epic since Epic 1, Story 7.7 aside (already fixed: see Previous Retro Follow-Through). 2 of the 5 reviews (9.1, 9.5) surfaced a genuine decision-needed question, both resolved by the user rather than assumed.

**Test growth:** backend 706 → 718 passed (12 net new, 9.1+9.2); frontend 404 → 423 passing (19 net new, 9.3+9.4+9.5). Zero regressions at every checkpoint, including after every review's patches.

**Production incidents:** 0 (local pilot, no production target).

**Blockers encountered:** none epic-specific, though see "recurring Docker staleness" below — a repeated friction point, not a blocker.

## What Went Well

- **Read-composition discipline held across both backend stories.** Neither 9.1 nor 9.2 added a new SQL query beyond what the existing dashboard endpoint already ran — 9.1 resurrected a safe-but-dead query pair (`list_assignments_for_dashboard`) rather than writing a new one, and 9.2 extended 9.1's exact fetch with a pure in-memory groupby. AR-26's "no new table, no new query pattern" goal was met by construction, not by after-the-fact review pressure.
- **A real would-have-shipped correctness bug was caught by reasoning, not luck.** Story 9.1's code review found that a video-duration fallback copied from the existing dashboard endpoint could trigger a database write (Content re-embedding) from what AC4 promised was a read-only `GET` — confirmed by reading `content/service.py::match_content_for_skill` directly, not assumed. The user made a real decision here (Action Item, resolved): drop the fallback for this endpoint rather than inherit the side effect, even though the sibling endpoint still has it.
- **Story 9.4 caught and then almost re-broke its own fix — and the second catch is the more instructive one.** Implementation fixed a real bug (the drill-down modal was only rendered in one of `DashboardPage.tsx`'s four state branches, so every deep link opened into a Loading skeleton with no modal). Code review then found that the fix itself was fragile: the modal was rendered at an *inconsistent child position* across those four branches, so React's positional reconciliation unmounted and remounted it on the realistic Loading→Loaded transition every deep link actually goes through — silently discarding the fix's own benefit. Both original tests happened to mock an empty grid, which hid the bug by coincidence. A new regression test now asserts `getDrillDown` fires exactly once across a real Loading→Loaded transition with non-empty rows.
- **A 2-epic-old escalated blocker finally closed, in the middle of this epic.** The Epic 7 retro flagged `authenticate()` still reading `_MOCK_ACCOUNTS` instead of the real `Account` table; the Epic 8 retro escalated it to top priority. It shipped 2026-09-14 — the same day as Stories 9.4/9.5 — via a direct bug-report investigation ("New employee functionality is not working"), not a formal Epic 9 story. The fix correctly triggered a fresh `AskUserQuestion` before touching auth code, applying a process lesson from *this same epic's own* Story 9.5 review (see below) within the same session it was written.
- **A new process lesson was created and then immediately self-applied.** Story 9.5's code review found that its `Login.tsx` redirect change (an auth-flow file) had exceeded the literal scope an earlier `AskUserQuestion` had confirmed ("frontend-only nav shell"). The user kept the change but the review recorded a standing lesson: *when a story's own research expands into a file/behavior category an earlier scope answer didn't cover — auth, security, cross-cutting config — raise a fresh `AskUserQuestion`, even after an earlier "proceed" answer.* The very next auth-touching change in this project (the `authenticate()` fix, same day) did exactly that.

## Challenges & What We Learned

- **A real, still-open security-adjacent gap was found twice and fixed zero times.** `RequireAuth.tsx` gates authentication only — there is no frontend role check on **any** HR page (`/dashboard`, `/hr/dashboard`, `/skills`, `/employees`). Access control for HR-only data relies entirely on the backend's 403 responses. First surfaced in Story 9.3's review (documentation inaccurately claimed both routes were "already role-gated"), confirmed again — independently — in Story 9.5's review, where the exact same inaccurate claim had been *repeated* in this story's own docs despite 9.3 having already corrected it once. Both times it was correctly scoped as pre-existing and out of story bounds, and both times it was logged to `deferred-work.md` — but never turned into a tracked `sprint-status.yaml` action item the way the `authenticate()` gap eventually was. Frontend `403`-only enforcement is defense-in-depth-missing, not defense-in-depth-redundant: any future client bug that swallows a 403 silently would leak an HR-only view with no second layer to catch it.
- **The same "stale Docker container" trap hit three stories in a row, and was never fixed at the root.** Stories 9.3, 9.4, and 9.5 *each independently* found `talentpilot-ui` (and, for 9.3, `talentpilot-api` too) unhealthy or hours-stale at session start before any live-browser verification could run — each time diagnosed and rebuilt manually, each time explicitly logged as "matching [the previous story]'s own already-documented trap." Three fixes of the same symptom is a process gap, not three independent problems: nothing changed about *how* these containers get started or watched between 9.3 and 9.5.
- **A real content-integrity bug slipped past the literal AC and was only caught because the reviewer read the actual spec text, not a paraphrase of it.** Story 9.3's Empty state dropped the entire top-line stats row, directly contradicting the UX spec's own literal instruction ("Stats show zeros; ring/pie chart area replaced with..."). The story's own Scope Note had silently paraphrased that clause away during authoring, and no test caught the gap because no test was written against the literal spec sentence — only against the paraphrase.
- **`ON_TRACK_THRESHOLD`'s actual comparison operator was never genuinely exercised until code review asked for it.** Every pre-review test for Story 9.2 sat at 0%, 100%, or a boundary case that was masked by a simultaneous Needs-Attention override — the `>=` itself was never proven correct at its own edge. Two boundary tests fixed this. Worth remembering as a specific pattern: a threshold constant needs at least one test that isolates *only* the comparison, with every other classification signal held constant.
- **A minor, partial recurrence of the Epic 8 retro's `project-context.md` gap.** That retro's Action Item 2 asked for a workflow gate ("a story cannot move to `done` without a matching entry") specifically because the reminder-only version had already failed once. The gate itself was never built (still `open`, see below) — and, sure enough, Story 9.1 has no direct `project-context.md` entry of its own; it is only referenced in passing from Story 9.2's entry. Not as severe as the 3-story gap that triggered the original action item, but the same shape of miss, on the very next set of stories after it was flagged.

## Next Epic Preview: Epic 10 — Post-MVP Admin & Roster Refinements

Unlike every prior retro in this project, Epic 10 isn't a blank slate to speculate about — it's already fully planned (16 stories, `prd.md` FR-34–FR-43, `epics.md`, all `backlog`) and extensively mocked in HTML (`_bmad-output/E-Development/01-Ritas-Trust-Call-Prototype/`), though **zero real backend/frontend code has been written for it.**

**Direct dependency on — and partial reversal of — this epic's own work:**
- **Story 10.11** removes Employee Segmentation (Stories 9.2/9.3/9.4's central deliverable — the pie chart, its endpoint, and its popover) from the dashboard entirely, replacing it with an Experience Distribution view. This was already confirmed as a deliberate, accepted product decision via `AskUserQuestion` during Epic 10 planning, not a surprise landing in this retro — but it means roughly three-fifths of Epic 9's frontend/backend surface is scheduled to be substantially rewritten or deleted before it ever reaches broad use. Story 9.1's stats/progress-ring half is unaffected and stays.
- **Story 10.12** amends Story 9.5's nav shell again — dropping the "Dashboard" entry down to 3 links, with the logo and default post-login landing taking over as the access point.
- **Story 10.15/10.16** (nav collapse, Company Name label) build further on the same `HrAppShell.tsx`/nav-shell surface Story 9.5 touched, currently proven out only in the HTML mockups, not the real component.

**What this means for Epic 10 kickoff:** whoever picks up Epic 10's first real story should read Story 9.2/9.3/9.4 *before* Story 10.11, not instead of it — Story 10.11's own AC already documents the swap, but the actual code being removed carries the two real lessons above (the read-only-write-path bug class from 9.1's review; the positional-remount bug class from 9.4's review) that a from-scratch Experience Distribution implementation could easily reintroduce if built without that context.

**Not carried forward automatically:** the frontend role-gate gap (above) will still be open when Epic 10's stories start touching these same pages again. Epic 10 introduces no new HR-only page, so it doesn't make the gap worse — but it also doesn't fix it, and every additional page built on `RequireAuth.tsx`'s current auth-only behavior is one more surface that inherits the same missing layer.

## Closing Notes

The headline pattern from every prior retro holds again: **every code review this project has run has found something real**, five for five this epic, continuing an unbroken streak since Epic 1 (Story 7.7 the sole historical exception, still awaiting its own review per an open action item). The more interesting thread this time is what happens *between* reviews rather than within one: a 2-epic-old escalated blocker finally closed mid-epic, using a process lesson generated by a review *within this same epic*, on the same day. That's the retro process working exactly as intended — and this retro closed the loop on its own lesson immediately rather than deferring it: the frontend role-gate gap, the same shape of finding as the `authenticate()` gap, was escalated to top priority here rather than left to need a third retro to catch.
