# Story 6.6: Live Content Search — YouTube (Per-Admin) & Udemy (Org-Wide) (FR-17, AD-7 branches 2 & 3)

Status: done

## Story

As an **HR Admin**,
I want to search YouTube and/or Udemy for content matching a Skill, live, on demand,
so that I can close a content gap for that Skill right now instead of waiting on the next scheduled batch run.

## Scope Notes (read before starting)

1. **API-only story.** Per a scope decision confirmed at story creation: the search UI (tabs, result cards, "Search Results" labeling, [View]/[Approve] buttons) is Story 6.10's job (epics.md line 2425 explicitly routes it through "Story 6.6's lookup endpoint"). This story delivers `POST /api/admin/skills/{id}/content-lookup` and its two source clients only — no frontend component, no dev route. Story 6.10 will be the first real UI consumer.
2. **Route lives in `skills/router.py`, logic lives in `content/service.py`.** This is the one open architectural composition this codebase hasn't needed before (flagged during story research): the URL is `/api/admin/skills/{id}/content-lookup` (same prefix as the existing Story 6.2/6.3 routes), but the actual search/credential logic belongs to `content/` (AD-1: only `content/` may import `youtube_client`/`udemy_client`/the credential tables). Resolved the same way `skills/router.py`'s existing routes stay thin: the route handler calls straight into a new `content.service.search_content_for_skill(...)`, which itself does the HR_ADMIN gate, the 404 check, and the actual search. The 404 check needs a `Skill` row without `content/` ever querying the `skills` table directly (AD-1/AD-8) — add a thin `skills.service.get_skill_by_id(db, skill_id) -> Skill | None` wrapper first, mirroring the existing `get_skill_embedding` wrapper's exact shape (`skills/service.py:52-55`). `content/service.py` calls that, not `skills.repository` directly.
3. **`content/repository.py` gets two new decrypt-and-return functions, not a change to the existing `get_admin_api_key`/`get_org_api_credential`.** Story 6.5 built those two to return the raw ORM row (still-encrypted) — this story is "the first caller that needs to call `decrypt_secret()` in a live code path" (Story 6.5 Dev Notes, explicit forward note). Add `get_decrypted_admin_youtube_key(db, *, admin_id) -> str | None` and `get_decrypted_org_udemy_credential(db) -> dict | None` (the latter returns `{"client_id": ..., "client_secret": ...}`, `json.loads()`'d after decrypt — Story 6.5 packed both fields into one encrypted JSON blob, documented on `OrgApiCredential`'s docstring). Both simply call the existing `get_admin_api_key`/`get_org_api_credential` then decrypt if found, returning `None` if the row doesn't exist — this IS this story's "no_credential" signal (no separate `configured` column, same as Story 6.5's `get_api_keys_status`).
4. **`content/service.py` gets a `_get_source_credential(db, *, admin_id, source)` orchestrator**, naming and shape taken directly from AD-10's own forward-looking text ("`content/service.py::get_source_credential(source, admin_id)` is the one place that reads... `CREDENTIAL_SCOPE = {YOUTUBE: PER_ADMIN, UDEMY: ORG_WIDE}`"). It does not decrypt itself — it dispatches to the two repository functions in Scope Note 3, keeping the decrypt boundary exactly where Story 6.5 put it (repository only).
5. **`udemy_client.py` is new and its exact request shape is a documented `[ASSUMPTION]`, not verified against a live Udemy for Business account.** No Udemy for Business sandbox credential exists in this environment. Built from Udemy's publicly documented Courses API v2.0 reference (confirmed via public search results, not a private/authenticated source): `GET https://{subdomain}.udemy.com/api-2.0/organizations/{account_id}/courses/list/`, HTTP Basic Auth (`requests`' `auth=(client_id, client_secret)`, base64-encoded automatically), `search=<query>` + `page_size=<n>` query params. Two consequences of this assumption, both flagged in code:
   - The endpoint URL needs an **organization subdomain and account id**, which are not part of the `client_id`/`client_secret` credential Story 6.5 stores (Udemy for Business assigns those per-portal, separately from API credentials). Added as two new **optional** `core/config.py` settings — `UDEMY_ORGANIZATION_SUBDOMAIN: str | None = None`, `UDEMY_ACCOUNT_ID: str | None = None` — mirroring `YOUTUBE_API_KEY`'s existing optional-with-None-default style so existing environments are unaffected. If Udemy's org-wide credential is configured (Story 6.5) but these two settings are not, `udemy_client.search_courses` raises a plain `Exception` (not `InvalidCredentialError`/`RateLimitExceededError`), which `content/service.py` classifies as `source_error` — a real, distinct-from-"no key" failure mode, not silently treated as "not configured."
   - Rate-limit signal: HTTP `429`, the universal REST convention (Udemy's own docs were not reachable to confirm the exact body shape) — trusted directly as the epics AC requires ("no local call counter"), same principle as `youtube_client.py`'s `QuotaExceededError`.
   - Invalid/revoked credential signal: HTTP `401`/`403` (Basic Auth rejection is standard for both).
   - `duration_hours` is best-effort parsed from Udemy's `content_info_short` field (a free-text string like `"10.5 total hours"`) via a small regex helper — returns `None` if the field is absent or doesn't match the expected pattern, never a guessed value.
6. **`youtube_client.py` gains one new exception class, `InvalidCredentialError`, additive and non-breaking.** The epics AC requires this endpoint to distinguish `invalid_credential` from `source_error` for **both** sources — YouTube's existing `search_videos` only ever raised `QuotaExceededError` (quota) or a bare `Exception` (everything else, including a bad key), because its only prior caller (`run_ingestion_job`) never needed that distinction. Detected the same way `_is_quota_exceeded` already works: a `400` response with `error.errors[].reason` of `"keyInvalid"` or `"badRequest"` (YouTube's documented invalid-API-key signal — `[ASSUMPTION]`, not verified against a live revoked key). This is purely additive: `run_ingestion_job`'s existing `except Exception` catch-all still catches the new exception (it subclasses `Exception`) exactly as before — zero behavior change for the existing ingestion path, confirmed by re-running `test_youtube_client.py`'s existing suite unmodified.
7. **Response shape is flat, not nested per-source.** The epics AC describes results and errors per-source but doesn't literally specify a response envelope. Chosen shape: `{ results: [Candidate...], errors: [{source, error}...] }` — successful sources contribute tagged (`source: "YOUTUBE"|"UDEMY"`) candidates to one flat `results` list, failed/unconfigured sources contribute one entry each to `errors`. Simpler than a nested `{youtube: {...}, udemy: {...}}` envelope and just as groupable by the future frontend (Story 6.10) via `result.source`. Document this choice inline in `content/schemas.py` since the epics text doesn't pin an exact envelope.
8. **Both sources are always attempted; the request body is exactly `{ query: str }`** (epics AC's literal wording — no `sources: [...]` selector field). A caller with only YouTube configured still gets a normal response: an empty-if-no-results `results` list plus one `no_credential` entry for Udemy in `errors`. This matches FR-17's "partial availability, not an all-or-nothing gate" consequence and PRD Open Question 18's stated (unconfirmed-but-adopted) assumption.
9. **No `content_catalog` row is written by this endpoint** (epics AC, explicit) — confirmed no call to `repository.create_content` anywhere in this story's new code; writing happens only in Story 6.8's (not-yet-built) approve action. This story is read/search-only.
10. **`AD-7`'s regression guard test needs updating, not left as-is.** `backend/tests/test_content_ad7_regression_guard.py` today bans the literal string `search_videos` and any import of `app.content.youtube_client` from every `router.py`/`main.py` — this story's own route calls straight into `content.service.search_content_for_skill`, which calls `youtube_client.search_videos`/`udemy_client.search_courses` internally, but no router file directly imports or names either. The existing guard would still technically pass (it doesn't inspect `content/service.py` at all), but the architecture spine's AD-7 text was explicitly amended (2026-09-08) to re-scope this exact guard: ban only `run_ingestion_job` and `settings.YOUTUBE_API_KEY` from any `router.py`/`main.py` (unchanged for the first symbol, new for the second) — `search_videos`/`udemy_client` calls reachable from a router are now legitimate. Update `FORBIDDEN_SYMBOLS`/`FORBIDDEN_IMPORT_SOURCES` to match the amended text exactly, and add a new assertion that no router/main file references `settings.YOUTUBE_API_KEY` (the shared batch key — this story's whole point is that the per-admin/org-wide keys are used instead, never that one).

## Acceptance Criteria

**Given** the existing `content/youtube_client.py::search_videos(api_key, query, max_results)` (Story 2.3 — already takes a caller-supplied key)
**When** I call `POST /api/admin/skills/{id}/content-lookup` with `{ query: str }` as HR_ADMIN
**Then** the handler fetches **my own** YouTube key from `admin_api_keys` (Story 6.5) and passes it as `api_key` — it **never** reads or references `settings.YOUTUBE_API_KEY` (the shared batch key). This is the boundary AD-7's regression guard now checks (re-scoped from "never call `search_videos`" to "never reference `settings.YOUTUBE_API_KEY` from a router")

**Given** I have no YouTube key configured
**When** I call this endpoint requesting YouTube results
**Then** the YouTube portion of the response is an explicit `{ source: "YOUTUBE", error: "no_credential" }` entry — not attempted, not a generic failure

**Given** the org-wide Udemy credential (Story 6.5)
**When** I call the same endpoint
**Then** a new `content/udemy_client.py` (mirroring `youtube_client.py`'s shape: a search function + a dedicated rate-limit exception) is called with the **org's** decrypted `client_id`/`client_secret` — never a per-admin key, since Udemy for Business issues credentials per organization (AD-7 branch 3)

**Given** a source's search fails (invalid/revoked credential, source API error, or a rate-limit response)
**When** the failure occurs
**Then** that source's entry in the response is a distinct error (`{ source: "...", error: "invalid_credential" | "rate_limited" | "source_error" }`) and the **other** source's results (if requested and configured) are unaffected — one source's failure never blocks the other (NFR-RES1)

**Given** `udemy_client.py`'s rate-limit handling
**When** Udemy returns a rate-limit response
**Then** it's detected via Udemy's **own** signal (HTTP `429`, per this story's documented `[ASSUMPTION]` — Scope Note 5) — no local call counter or concurrency semaphore is built (Deferred, AD-7's Deferred section: "premature to build now" at this pilot's scale)

**Given** either source returns results
**When** the response is assembled
**Then** each result includes `{ title, source: "YOUTUBE" | "UDEMY", url, thumbnail_url, duration_hours | null }` — no `content_catalog` row is written by this endpoint (search-only; writing happens in Story 6.8's approve action)

**Given** an EMPLOYEE session
**When** it calls this endpoint
**Then** `403 Forbidden` (AD-6)

**Out of Scope (this story):** the "Currently Approved" section shown alongside search results in the UI (Story 6.10 reads it via a separate, existing read of `content_catalog` — this endpoint is search-only, it doesn't need to know what's already approved). The search UI itself (Story 6.10, Scope Note 1).

## Dev Notes

- **Why the route lives in `skills/router.py` rather than a new `content/content_lookup_router.py`:** epics.md's own Architecture spine (line 149) names the URL `/api/admin/skills/{id}/content-lookup` explicitly in the Consistency Conventions table, already grouped with the other `/api/admin/skills/*` routes — treating it as a sibling of the existing Story 6.2/6.3 routes (same prefix, same file) is more consistent than introducing a third routing file for one endpoint. The actual search logic still lives in `content/`, preserving AD-1 or (content/ owns youtube_client/udemy_client/credentials, skills/ never imports them).
- **This is the first story where `skills/router.py` calls into `content/service.py`.** Every prior cross-module composition in this codebase has content/assignments depending on skills, never the reverse at the router layer — this is a new, one-directional edge (route only, not a service-to-service call), justified because the URL path (a Skill sub-resource) and the business logic (content search) genuinely belong to different modules. Does not violate AD-8's diagram (`Content -.-> Skills`), which describes service-layer dependencies, not which router file physically hosts a route.
- **`youtube_client.py`'s new `InvalidCredentialError` and `udemy_client.py`'s exceptions are deliberately not unified into one shared exception hierarchy.** Considered a shared `app.content.errors.InvalidCredentialError`/`RateLimitExceededError` module both clients raise, but rejected it: `youtube_client.py` and the not-yet-written `udemy_client.py` are independent, source-specific wrappers by design (Story 2.3's original intent, reaffirmed by this story's own Scope Note 5 calling `udemy_client.py` a mirror of `youtube_client.py`'s *shape*, not a shared base). `content/service.py`'s classification logic (Task 7) simply catches each module's own exception types by name — four small `except` clauses, not a shared enum lookup, matching this codebase's general preference for explicit per-branch handling over cross-cutting abstraction (see `run_ingestion_job`'s own `except youtube_client.QuotaExceededError` / `except Exception` split).
- **Duration parsing is two genuinely different problems for the two sources** — YouTube's `get_video_durations` already returns a real ISO-8601 string (`content/service.py`'s `ingest_content_for_skill` just stores it as-is today, never converting to a float); this story is the first caller that needs `duration_hours: float`, so `_parse_iso8601_duration_hours` is new. Udemy's `content_info_short` is free text, not a structured duration at all — its parser is inherently lossier (best-effort regex, documented `None`-on-miss behavior) and is a separate, independent helper in `udemy_client.py` rather than a shared "parse duration" utility, since the two input formats have nothing in common.
- **Not touched, deliberately:** `content/router.py` (the pre-existing `/api/content` `GET /match` route — unrelated), Story 6.5's `admin_api_keys_router.py` (read-only status endpoint, this story only reads the two underlying tables via new repository functions), `content_catalog`/`ContentCatalog` (no write path here, Scope Note 9), the Skills tab frontend (Story 6.10).
