# Epic 7 Retrospective: Employee Roster Management

Run **out of order**, same as the Epic 6 retro immediately before it: Epic 8 (Application Theming) was planned alongside Epic 7 and already shipped in full by the time this retro runs. Part 2 is therefore reframed from forward-looking "next epic preparation" into (a) a continuity check of whether Epic 7's work destabilized Epic 8, and (b) real, unresolved gaps left inside Epic 7 itself that don't need a new epic to fix — they need someone to pick them up.

## Epic Summary

**Epic 7 — Employee Roster Management:** 7/7 stories done (7.1–7.7). New `employees/` module (schema, bcrypt credential storage extending the existing-but-previously-unused `Account` model), full Employee CRUD (create/view/edit/delete-or-archive/regenerate password), and a left-pane navigation shell replacing the old top-header nav across every HR Admin page. Realizes FR-24 through FR-29.

**Velocity:** planned 2026-09-11 (same planning session as Epic 8), all 7 stories implemented and reviewed by 2026-09-12 — about two days, matching Epic 6's pace as the fastest epics in the project.

**Quality:** Stories 7.1–7.6 each received a full 3-layer adversarial code review (Blind Hunter / Edge Case Hunter / Acceptance Auditor). **Every one of those six reviews found and fixed real bugs** — continuing the streak this project has now observed in every epic since Epic 1. **Story 7.7 (nav shell) is the first story in this project's tracked history to skip code review entirely** — it went from implementation straight to `done`, with a much thinner story file (a "what shipped" summary, not the full spec-with-Dev-Notes format every other story in this project uses).

**Production incidents:** 0 (local pilot, no production target).

**Blockers encountered:** none epic-specific.

## What Went Well

- **`skills/`-extraction pattern reused cleanly for `employees/`.** Story 7.1 explicitly mirrored Story 6.1's module-relocation shape (physically move the model, register via whole-module import both directions) — the exact pattern Story 6.1's own code review had to fix twice before it was airtight came out correct on the first try this time.
- **Cross-story component/helper reuse stayed disciplined.** `generate_password`/`hash_password` (7.1) fed both 7.2 (create) and 7.6 (regenerate) unchanged; `_has_any_history_for_employee` (7.5) was reused as-is by 7.6's archived check; `EmployeeCreatedResponse` was deliberately reused for password reveal instead of a new schema, per the epic's own explicit instruction.
- **7.7's shell extraction paid off immediately in Epic 8.** `HrAppShell.tsx` consolidated three near-identical, drifted header blocks (`Dashboard.tsx`/`SkillsPage.tsx`/`EmployeesPage.tsx`) into one component — and Story 8.1's dark-mode toggle placement notes confirm it covered all three pages "for free" as a direct result, with no extra wiring needed. A real, measured payoff from doing the consolidation, not just a tidiness win.
- **Two hard, non-obvious architecture calls were resolved cleanly and documented for reuse, not punted.** Story 7.1 resolved AR-24 (where Employee credentials live) by discovering `core/seeds.py` already implicitly assumed `Account.id == Employee.id` and formalizing that with a real FK, rather than inventing a new column. Story 7.5's atomicity requirement (race-safe hard-delete-vs-archive) was solved with a `SELECT ... FOR UPDATE` lock reasoned correctly against Postgres's actual `FOR KEY SHARE` FK-insert locking semantics — a genuinely non-trivial concurrency argument, worked through and verified rather than guessed at.

## What Slowed Us Down / Challenges

- **Story 7.7 shipped with no adversarial code review.** Every other story this epic (and every story in this project since Epic 1) got a 3-layer review, and every single one of those reviews found something real — several of them serious (see below). 7.7 touches the shared shell every HR Admin page now depends on, and its own story file names its own gap: no live-browser verification was possible in the sandbox, so responsive behavior (sidebar collapse, hamburger overlay, backdrop dismiss at 375/768/1280px) is verified only via class-level assertions against the prototype's Tailwind classes, not a rendered check. That gap was flagged in the story file itself — but no code-review pass was ever run to catch anything beyond it.
- **The same bug classes recurred from prior epics, not new ones.** Story 7.4 hit the exact `MissingGreenlet` pattern (reading an ORM attribute after `await db.rollback()` expires it) already documented from Stories 1.1/1.2/6.4/6.5 — a fourth occurrence of a lesson that keeps needing to be re-learned per-story rather than caught by convention or a lint rule. Story 7.5 found a new variant of an old lesson: a `None`-guard fix applied to one function in a diff (`delete_account`) wasn't copied to a sibling function added in the *same* diff (`update_account_archived_at`) — the fix propagating within a diff isn't automatic just because the pattern is fresh in the author's mind.
- **A real self-lockout bug reached review, not before.** Story 7.5 shipped with no self-deletion guard — TalentPilot, this project's only real interactive HR Admin, could have archived their own account and then immediately failed their own next authenticated request (Story 7.5's own new AR-25 check), with no un-archive path to recover. Caught in code review, not design — worth remembering as a class of bug ("can this actor delete/disable themselves with no recovery path") worth a standing checklist item for any future admin-self-service story.
- **An audit-integrity bug directly contradicting the epic's own stated purpose.** Re-archiving an already-archived Employee silently overwrote `archived_at`'s original timestamp — destroying exactly the audit trail FR-27 exists to preserve. Also caught only in review.
- **The accessibility gap from Epic 6 recurred a third time, still unfixed.** No `aria-required` marker on required fields, no `aria-describedby`/`role="alert"` linking a duplicate-value notice to its input — first flagged as a `NewSkillModal.tsx` gap in Epic 6, it now also exists identically in `EditEmployeeModal.tsx` (7.4) and (by the same pattern) the Create Employee flow (7.2). Each time it's deferred as "matches existing precedent," which is true but means the precedent itself has never been fixed.
- **Story 7.6 surfaced a new lesson worth keeping**: its own Dev Notes argued no `FOR UPDATE` lock was needed because there was "no multi-step decision a concurrent write could invalidate" — but that reasoning missed the `await` inside `asyncio.to_thread(hash_password, ...)`, a real TOCTOU window a concurrent archive could land in. Fixed in review. The lesson is specific: reasoning about concurrency safety has to account for every `await` in a function, not just the ones between its explicit decision branches.
- **This project's own `project-context.md` file admits it failed its own mandatory-update rule for two epics' worth of work.** That file's first section is a standing rule that it must be updated "every time any meaningful work happens on this project" — but its own log has a gap note admitting Stories 6.6 through 7.3 were implemented with no corresponding entry ever appended. It resumed at Story 7.4. A memory file that documents its own violation of its own top-billed rule is worth fixing going forward, not just noting once.

## Significant Discoveries

**One discovery is significant enough to flag prominently, though it does not require re-planning already-shipped work:** the entire real-credential system this epic built (bcrypt hashing, generated/regenerated passwords, archived-account session invalidation) is currently **inert** at the one place that matters most — the actual login endpoint still only recognizes Story 1.4's five hardcoded demo accounts. This isn't a bug introduced by any single story; each story that touched it (7.1, 7.4, 7.6) correctly scoped `authenticate()`'s rewiring as out-of-bounds and flagged it forward. But it was flagged forward three times and captured as a tracked action item zero times, until this retro (Action Item 3). No epic re-plan is needed — Epic 8 didn't depend on this and wasn't affected — but this should not go into a hypothetical Epic 9 as quietly as it's traveled through Epic 7.

No other discovery requires re-planning already-shipped work.

## Closing Notes

The headline pattern holds again this epic: **every code review found something real** — except the one story that didn't get one. That is not a coincidence worth ignoring. Story 7.7 is low-risk in isolation (frontend-only, well-tested, no backend surface), but it is also the shared shell every other HR Admin page now renders through, which is exactly the kind of high-blast-radius surface this project's own reviews have repeatedly proven worth scrutinizing. The other standout thread is the credential-wiring gap: three stories individually made the right call to scope it out, and the sum of three correct individual decisions was a real capability quietly never landing. Worth remembering as a retro-specific lesson: a gap flagged forward in Dev Notes needs to also become a tracked action item, or it can survive an entire epic unassigned.
