# Story 7.5: HR Admin Deletes or Archives an Employee Record

Status: done

## Story

As an **HR Admin**,
I want to remove an Employee who has left, with their history preserved if they were ever assigned anything,
So that the roster stays accurate without destroying audit history (FR-27).

## Scope Notes (read before starting — this story is larger than a typical single-module CRUD story per epics.md's own flag)

This story touches three separate surfaces across two other epics, confirmed by direct code reading during story authoring:

1. **`archived_at` already exists on `Employee`** (Story 7.1, `backend/app/employees/models.py:62`, migration `011_add_employee_profile_fields.py:44`) — `null` = active, non-null = archived. `EmployeeResponse` already exposes it (`schemas.py:102`). No new column needed on `employees`.

2. **New route: `DELETE /api/admin/employees/{employee_id}`**, mounted on the already-existing `employees_router` (no new `main.py` mount). Unlike `deleteSkill`'s `Promise<void>` convention (`frontend/src/lib/api/skillsApi.ts`), this endpoint returns a body — `{"action": "deleted" | "archived"}` — because the frontend's success toast copy depends on which action actually occurred, and (per point 4 below) the server may decide differently than what the confirmation dialog predicted. This is a deliberate, justified departure from the `deleteSkill` shape, not an oversight.

3. **Atomicity mechanism for AC1/AC2 (the "check-then-act must be one atomic operation" requirement) — a `SELECT ... FOR UPDATE` row lock, not a SERIALIZABLE transaction.** `backend/app/employees/repository.py` gains `get_employee_for_update(db, employee_id) -> Employee | None` using `select(Employee).where(Employee.id == employee_id).with_for_update()`. This works because `assignments.employee_id` has `ForeignKey("employees.id")` (`backend/app/assignments/models.py`) — Postgres takes an implicit `FOR KEY SHARE` lock on the referenced `employees` row whenever a new `Assignment` INSERT targets it, and `FOR KEY SHARE` conflicts with `FOR UPDATE`. So: holding the employee row's `FOR UPDATE` lock for the whole duration of this service call blocks any concurrent `create_assignment_service` call targeting the same employee from completing its INSERT until this transaction commits or rolls back — no separate SERIALIZABLE isolation level or advisory lock needed. Document this reasoning inline in the service function; it is the load-bearing correctness mechanism for AC1/AC2 and AC5's race scenario (see point 6).

4. **The "decided server-side, shown before confirm" requirement (UX-DR38) vs. the "atomic re-check at confirm time" requirement (AC1/AC2) are reconciled by splitting them into two separate reads, not one:**
   - **Preview (dialog copy):** `EmployeeResponse` (`employees/schemas.py`) gains `has_assignment_history: bool` (default `False`, mirroring `SkillResponse.ever_assigned`'s established shape from `frontend/src/lib/api/skillsApi.ts:8` / the Skills module). Computed via a new `assignments/service.py::get_employee_ids_with_assignment_history(db) -> set[UUID]` (single `SELECT DISTINCT employee_id FROM assignments` — deliberately **unfiltered on `active`**, since FR-15 soft-deleted Assignments still count as "history ever existed", per this story's own AC1 wording "active or soft-deleted"). `employees/service.py::list_employees_service` calls this once for the whole roster (not per-row — avoids N+1) and sets `.has_assignment_history` on each already-validated `EmployeeResponse` object (Pydantic v2 models are mutable by default; this is a two-pass "validate, then patch the one computed field" idiom — do not try to smuggle it through `model_validate(employee)` in one call, since `has_assignment_history` isn't a real ORM column and `from_attributes=True` would look for a real attribute). This field drives the confirmation dialog's copy from data the roster page already has in memory — no fresh per-click "preview" network call, consistent with this codebase's two existing precedents for conditional-copy modals (`SkillCard.tsx`'s `ever_assigned`, `DeleteAssignmentModal.tsx`'s `hasRecordedProgress`).
   - **Actual decision (confirm-time):** the `DELETE` endpoint independently, atomically re-decides which action to take (point 6) regardless of what the dialog displayed, and its response's `action` field — not the dialog's prediction — is what the success toast reflects. In the rare race where an Assignment was created between dialog-open and confirm-click, the toast will correctly say "archived" even if the dialog predicted "removed"; this is expected and correct, not a bug to "fix" by re-fetching before confirm.
   - `update_employee_service` and `create_employee_service`'s existing `EmployeeResponse.model_validate(employee)` calls also need this field set correctly (a freshly-created employee is always `False` by construction — zero Assignments can exist yet; an edited employee needs a fresh single-employee check via a new `assignments/service.py::has_assignment_history_for_employee(db, employee_id) -> bool`, an `EXISTS`-style query, not a full-list scan). Add a small `employees/service.py::_with_assignment_history(response, has_history)` helper (or equivalent inline pattern) used consistently by all three service functions so this doesn't drift.

5. **Hard-delete must also delete the paired `Account` row.** `Account.id == Employee.id` (shared PK, `backend/app/auth/models.py:40`, AR-24) — hard-deleting `Employee` without deleting the matching `Account` row leaves it orphaned. `auth/repository.py` gains `delete_account(db, *, id: UUID) -> None` (guard the `db.get(Account, id)` result for `None` before deleting — don't reintroduce the unguarded-`db.get()` pattern already flagged as deferred-but-unreachable in Story 7.4's review; it becomes reachable the moment this story ships). This mirrors the existing test helper `test_employees_router.py::_delete_employee_by_code`, which already deletes `Account` then `Employee` in that order — a real, already-established precedent, not a new idea.

6. **`[REVISED 2026-09-12, code review]`** The "zero Assignment records ever created for them" check (AC1) is about `Assignment.employee_id == this employee` — i.e., "were they ever the *target* of an assignment" (matches FR-27's plain wording). But six real FK columns reference `employees.id` across three modules and would equally block a hard-DELETE with a Postgres `IntegrityError` if the employee being deleted has ever acted in any of these roles: `Assignment.assigned_by`/`deleted_by` (assignments/), `AssignmentOverride.set_by`/`reversed_by` (progress/ — not `created_by`, an earlier draft of this note got the column name wrong), and `AdminApiKey.admin_id`/`ContentCatalog.attached_by` (content/, also missed in the earlier draft). **Final design (post code-review): pre-check all six via `employees/service.py::_has_any_history_for_employee`** (three cross-module service calls per AD-1 — `assignments.service`, `progress.service.ProgressService`, `content.service` — each exposing a thin wrapper over its own owned table(s)), rather than the originally-planned "don't pre-check, just catch the IntegrityError" approach. This was upgraded because the narrower check meant the Delete/Archive confirm dialog's `has_assignment_history` prediction would always be wrong for any employee who had acted in one of these roles (in practice, this app's only real interactive HR Admin) — the dialog would say "Remove Employee" while the server always archived instead. The pre-check now drives *both* the dialog's preview *and* the actual hard-delete-or-archive decision, so they can never disagree. The `try/except IntegrityError` around the hard-delete attempt remains as a defensive-only backstop (narrowed to the FK-violation SQLSTATE, `23503`, re-raising anything else) for any FK relationship a future migration adds that this pre-check doesn't yet know about — not the primary mechanism anymore. After a rollback on that backstop path (which releases the `FOR UPDATE` lock and expires `employee`'s attributes — use the `employee_id` parameter, not `employee.id`, exactly per Story 7.4's documented `MissingGreenlet` lesson), **re-acquire the row lock** via `get_employee_for_update` again before archiving, since the lock was dropped by the rollback.

## Acceptance Criteria

**AC1 — Zero Assignment history → atomic hard-delete:**
**Given** an Employee has zero Assignment records (active or soft-deleted, per FR-15) ever created for them
**When** I confirm deletion
**Then** the record is hard-deleted — the check-then-delete executes as a single atomic operation (not a separate read then write), so a concurrent Assignment-creation request cannot race past this check (mirrors FR-7's concurrency discipline).

**AC2 — Any Assignment history → archive instead:**
**Given** an Employee has any Assignment history
**When** I confirm deletion
**Then** the record is archived instead (`archived_at` set, per Story 7.1) — not deleted — and drops off the default roster view (Story 7.3) and every Employee picker (e.g., the Skill Assignment Flow), while all their Assignment/Watch-Progress/Override history remains fully intact.

**AC3 — Confirmation copy states the outcome before confirm:**
**And** the confirmation dialog states which behavior will occur (hard-delete vs. archive) *before* I confirm — decided server-side and reflected in the copy, never guessed client-side (UX-DR38).

**AC4 — Archived Employee's live session is rejected on the next request:**
**Given** an archived Employee has a valid, unexpired session token
**When** they make any subsequent protected request after being archived
**Then** the request is rejected — session validity is revalidated against current active/archived status server-side on every request, not only checked at login time (AR-25); this requires the existing per-token revocation mechanism (Story 1.5) to be extended with a per-identity active-status check.

**AC5 — Stale Assignment picker rejected at confirm time, not just load time:**
**Given** an HR Admin has the Skill Assignment Flow's employee picker open (loaded before an archive) and another HR Admin archives that same Employee
**When** the first HR Admin attempts to confirm a new Assignment against the now-archived Employee
**Then** the request is rejected server-side at confirm time, not only at picker-load time, with a clear error prompting a re-pick from the current roster.

## Dev Notes

### Why this story cannot be estimated/reviewed as routine CRUD (epics.md's own warning, confirmed true during authoring)

Three genuinely separate correctness mechanisms are needed, each in a different module: (1) an atomic check-then-act via row locking in `employees/`, (2) a session-validation change in `auth/service.py` touching every protected request in the app, and (3) a new pre-write validation in `assignments/service.py`'s already-shipped, `done` create-assignment path. None of these can be built in isolation from the others without breaking one of the five ACs — see Scope Notes 3/6/7/8 for exactly how they interlock (in particular, the `FOR UPDATE` lock from mechanism (1) is what makes mechanism (3)'s race-condition AC actually correct, not just independently plausible).

### The one thing this story deliberately does NOT do

No un-archive/restore capability is built here (PRD §6.3's open assumption: "an archived (soft-deleted) [Employee] can be un-archived by an HR Admin... not independently confirmed"). This story only ever sets `archived_at`; nothing clears it. Don't add an un-archive endpoint "for completeness" — it's out of this story's AC scope.

### `authenticate()`'s pre-existing mock-account gap is orthogonal to this story

`auth/repository.py::authenticate()`/`find_account()` still only reads the hardcoded `_MOCK_ACCOUNTS` dict (unchanged since Story 1.4, reconfirmed unrelated by Story 7.4). This story's AC4 mechanism (checking `Account.archived_at` inside `get_current_user`) works identically regardless of that gap, because both the mock-login path and any future real-`Account`-backed login path mint JWTs carrying the same real Employee/Account UUID as `user_id` — session validation and login-time credential lookup are two independent code paths that happen to share the same identity space. Don't let this story's implementation accidentally couple the two.

## Architecture Compliance

- **AD-1**: `employees/repository.py`/`auth/repository.py`/`assignments/repository.py` each own their own table's reads/writes. The one genuinely new cross-module edge (`assignments/service.py` importing `employees/service.py` for AC5) goes through the service layer, not a repository reach-around — this is the *normal* AD-1 pattern already used elsewhere in this codebase (e.g. `assignments/service.py` already imports `skills/service.py::mark_ever_assigned`), not an exception like the `employees/service.py` → `auth/repository.py` direct-write pattern is (Scope Notes 5/7 explicitly name that one as the third and final planned use of that specific exception).
- **AD-6/FR-14**: `DELETE /api/admin/employees/{employee_id}` is HR_ADMIN-only via `require_hr_admin`, matching every other `/api/admin/*` mutation in this codebase.
- **AR-25** (epics.md-only, no spine AD yet): realized here by extending AD-6's per-request identity resolution (`get_current_user`) with a live `Account.archived_at` check — see Scope Note 7 for why this doesn't require importing `Employee` into `auth/`.
